## 1. 技术选型

### 1.1 选型结论

| 层面 | 选型 | 理由 |
|---|---|---|
| 语言 / 运行时 | **C# / .NET 8**（x64） | 见 §1.2 |
| UI 框架 | **WinUI 3**（Windows App SDK） | 满足 NFR-10 / NFR-11 / §6.4 |
| 平台 API | **Win32 P/Invoke**（User32 / Kernel32 / Registry） | 输入模拟、全局钩子、坐标、自启 |
| 配置格式 | **JSON**（`System.Text.Json`） | 见 §7.1 |
| 分发形态 | 非打包 + 宿主单文件自包含（§1.4） |

### 1.2 语言选型的理由

本项目的性能瓶颈**不在语言本身**，而在一条架构约束（见 §3.2：钩子回调必须立即返回）。C# 完全能守住该约束，而它在 UI 开发效率上显著优于 C++，且 WinUI 3 对 C# 是一等公民支持。

- **不选 C++**：能力上够，但对本项目是过度投入——GUI 开发成本高，而收益（更低延迟）在需求口径（NFR-01 ≤50ms、NFR-02 ±20ms）内体现不出来。
- **不选 Rust**：WinUI 3 无官方 Rust 绑定，选它就得放弃原生 UI 栈，与 NFR-10（Windows 原生视觉风格）直接冲突。
- **不选 WPF / WinForms**：属 .NET 上一代 UI 技术，控件外观非 Windows 11 原生，与 NFR-10 冲突。

### 1.3 WinUI 3 的适配性（依据）

WinUI 3 官方定位："用于构建新的 Windows 桌面应用程序的推荐原生 UI 框架"，"可用于创建在 **Windows 10 版本 1809（内部版本 17763）** 及更高版本上运行的现代、美观和响应式桌面体验"，且 "Windows shell 及其内置应用的某些部分是使用 WinUI 生成的"。

| 需求 | WinUI 3 如何满足 |
|---|---|
| NFR-10 原生风格 + 简约 | WinUI 3 即 Windows 自身的设计语言（Fluent），控件与系统主题（深/浅色）自动同步 |
| NFR-11 过渡动画 + 尊重"减少动画" | WinUI 3 动画系统基于系统合成器，随系统辅助功能设置自动减弱 |
| §6.4 最低 Win10 1809 | 与 WinUI 3 官方支持线完全一致 |
| FR-UI-04 固定取值用选择控件 | ComboBox / RadioButtons / ToggleButton 等原生控件直接覆盖 |

**待评审确认的取舍**：WinUI 3 应用**不支持系统托盘**（`Shell_NotifyIcon` 无 WinUI 封装）。因此托盘（FR-UI-01/02）需通过 **Win32 互操作**实现——自己调用 `Shell_NotifyIcon` 并处理其回调消息。这是本选型唯一的明显代价，方案见 §6.3。

### 1.4 分发形态（已确定）

- **打包方式：非打包（unpackaged）**。排除 MSIX 的理由是三处结构性冲突（非偏好取舍）：① MSIX 应用无 `requireAdministrator` 清单能力——包按设计运行在受限令牌下，与已裁定的“宿主进程整体提权”（NFR-06 / §8 / Q-D3）**直接冲突**；② `%APPDATA%` 被重定向到包容器（`...\Packages\<包名>\LocalCache\Roaming\...`），FR-CFG-01 要求的路径不再成立；③ 不能直接写 `HKCU\...\Run`，FR-UI-03 的开机自启需改用 MSIX 的 `StartupTask` 扩展声明。三者均需回头修改已冻结需求或已裁定项，代价远大于非打包的部署便利损失。非打包亦更贴合本工具“绿色常驻”的定位。
- **宿主可执行体：单文件自包含（self-contained single-file）**。不依赖目标机预装 .NET 8 运行时，拷贝即用；代价是体积增大（约 150MB+）——对本工具“必须提权运行、多一步安装就多一道障碍”的场景，该代价可接受。
- **两个可执行体，职责分离（见 §2.2）**：外层 `Launcher.exe`（普通权限，清单**不**请求提权）负责启动内层并捕获提权失败；内层 `鼠标键盘辅助.exe`（清单 `requireAdministrator`）为业务宿主。**两层不能合并为单个 EXE 的双模式**：若同一 EXE 带 `requireAdministrator` 清单，外壳自身也会被强制提权，从而丧失“以普通权限弹出提权失败提示”的能力（AC-26）。
- 具体 .NET 版本补丁与 Windows App SDK 版本号仍待实现期定（不影响本决策）。

> 上述选择只影响安装与部署，**不影响 §2 的架构判断**（模块划分、进程/线程模型、输入层设计三者与打包方式无关）。

## 2. 总体架构

### 2.1 分层

```
┌─────────────────────────────────────────────┐
│  UI 层（WinUI 3）                            │
│  任务列表 / 任务编辑 / 设置页 / 托盘菜单       │
└───────────────┬─────────────────────────────┘
                │ 调用（命令式）
┌───────────────▼─────────────────────────────┐
│  应用核心（Engine）                           │
│  ┌──────────┐ ┌──────────┐ ┌──────────────┐ │
│  │ 任务仓库  │ │ 任务调度  │ │ 配置持久化    │ │
│  │ Registry │ │ Scheduler│ │ ConfigStore  │ │
│  └──────────┘ └────┬─────┘ └──────────────┘ │
└────────────────────┼────────────────────────┘
                     │
┌────────────────────▼────────────────────────┐
│  输入层（Input）                              │
│  ┌────────────┐  ┌──────────────────────┐   │
│  │ 全局钩子    │  │ 输入模拟引擎          │   │
│  │ HookService│  │ InputSimulator       │   │
│  └────────────┘  └──────────────────────┘   │
└─────────────────────────────────────────────┘
                     │
              Win32 API（User32 / Kernel32 / Registry）
```

### 2.2 模块职责与依赖

| 模块 | 职责 | 依赖 | 对应需求 |
|---|---|---|---|
| **UI 层** | 呈现与交互：任务增删改、按键捕获、状态显示、设置页、托盘 | Engine | FR-TASK-01~06、FR-TOGGLE-02/04、FR-UI-01~05 |
| **任务仓库 Registry** | 内存中的任务集合、唯一性校验、冲突校验、状态机（运行/停止/启用/禁用） | — | FR-TASK-06~09、FR-TOGGLE-05/07、FR-SEQ-08/10、NFR-09 |
| **任务调度 Scheduler** | 任务启停、每条命令的独立定时循环、并行编排、停止时补发松开 | InputSimulator | FR-SEQ-01~07、FR-TAP-*、NFR-01/02/03 |
| **配置持久化 ConfigStore** | 配置读写、损坏回退、版本兼容 | Registry | FR-CFG-01~05 |
| **全局钩子 HookService** | 监听键盘/鼠标低级事件，识别开关按键与紧急停止 | —（向上投递事件） | FR-TOGGLE-06、FR-RUN-01、§6.1 |
| **启动壳 Launcher** | 独立可执行体 `Launcher.exe`（普通权限，清单**不**请求提权）：启动宿主并捕获提权被拒，随即告知用户（AC-26）。不承载业务逻辑 | — | NFR-06、AC-26 |
| **日志 Logger** | 记录任务启停与错误事件 | — | FR-CFG-05 |

**依赖方向**：UI → Engine → Input。Input 层不反向依赖 Engine（它只投递事件，由 Engine 订阅），避免循环依赖。**Launcher 独立于上述三层**：它不参与运行时架构，只在启动阶段存在（详见 §8 权限口径）。

### 2.3 数据流（一次开关键点按的全过程）

```
用户按键
  → HookService 钩子回调（钩子线程）
      ① 判定：是否匹配某个已启用任务的开关按键？
      ② 立即投递事件到事件队列，钩子回调随即返回（不在此处执行任何输入模拟）
  → Engine（工作线程）从队列取出事件
      ③ 切换任务状态：停止 → 启动 / 运行 → 停止
      ④ 若为"启动"：为任务的每条命令创建定时循环（并行）
         若为"停止"：终止全部循环，补发"按住中"按键的松开事件
  → InputSimulator 在工作线程上调用 SendInput 发出事件
  → UI 通过数据绑定/事件收到状态变更通知，更新显示（FR-TOGGLE-04）
```

**关键点**：第 ② 步的"立即返回"是整个架构的安全绳（依据见 §3.2）。

## 3. 输入层设计

### 3.1 输入模拟：SendInput

选用 Win32 `SendInput`（`user32.dll`）作为唯一的输入模拟出口，不使用 `keybd_event` / `mouse_event`（旧式 API，微软文档已将其列为被 `SendInput` 取代，且日志钩子 API 已废弃并"强烈建议改为调用 SendInput"）。

`SendInput` 的语义要点（决定实现细节）：
- 事件**串行插入**输入流，与用户物理输入或其他调用产生的输入**不会交错**；
- 受 **UIPI** 约束："仅允许应用程序将输入注入到完整性级别相等或更低级别的应用程序"——这解释了 FR-RUN-01 与 NFR-06 为何需要管理员权限；
- **不会重置键盘当前状态**："调用函数时已按下的任何键都可能会干扰此函数生成的事件"，文档建议用 `GetAsyncKeyState` 检查并按需纠正。

**设计定位**：`InputSimulator` 是**唯一**调用 `SendInput` 的地方，向上暴露语义化方法：

```
TapKey(vk)                  // 按下 + 松开（点按）
HoldKey(vk)                 // 仅按下
ReleaseKey(vk)              // 仅松开
TapMouseButton(button)
HoldMouseButton(button)
ReleaseMouseButton(button)
MoveMouseAbsolute(x, y)     // 绝对坐标
ScrollWheel(direction, notches)
TapCombo(modifiers, vk)     // 修饰键↓ → 主键↓↑ → 修饰键↑
HoldCombo(modifiers, vk)    // 修饰键↓ → 主键↓（保持）
```

`InputSimulator` 内部维护一个**"当前按住集合"**（按下的键/键鼠按钮的集合），这是 FR-SEQ-07 / FR-RUN-05 补发松开的**唯一权威来源**——不靠遍历命令反推，而是记录实际按下、尚未松开的事件。

### 3.2 全局钩子：钩子回调短小化（架构硬约束）

选用 `SetWindowsHookEx(WH_KEYBOARD_LL / WH_MOUSE_LL)` 实现全局监听（FR-TOGGLE-06）。微软文档给出三条必须遵守的约束：

| 文档原文要点 | 对本设计的要求 |
|---|---|
| "挂钩过程处理消息的时间应短于 `LowLevelHooksTimeout`"；"如果挂钩过程超时……在 Windows 7 及更高版本上，挂钩以**静默方式删除**，无需调用。**应用程序无法知道挂钩是否已删除**" | 钩子回调**绝不做重活**——不调 `SendInput`、不写文件、不做 UI 更新 |
| "安装挂钩的线程**必须具有消息循环**" | 钩子安装在一个**专用线程**上，该线程运行消息泵 |
| "应在将工作传递给工作线程、然后**立即返回**的专用线程上运行挂钩" | 即上面的专用线程；判定后把事件投递出去就走 |

**另外两条必须处理的约束**：
- `WH_KEYBOARD_LL` / `WH_MOUSE_LL` **仅支持全局范围**（文档明列）；
- "**全局挂钩函数必须位于库（DLL）中**"——低层钩子（LL 型）的特殊之处在于：钩子回调在安装它的线程上下文中被调用，**不注入其他进程**（文档明确："WH_KEYBOARD_LL 挂钩不会注入到另一个进程中。相反，上下文将切换回安装挂钩的进程"）。因此本设计**无需额外的独立 DLL**，回调可留在主程序集内——但**必须保证回调不被 GC 移动**（文档："在 .NET 应用中，必须确保垃圾回收器不会移动回调（否则你的应用会因 ExecutionEngineException 而崩溃）。执行此操作的一种方法是将回调设置为类的静态方法"）→ 回调实现为**静态方法**并持有委托引用。

**超时风险的应对**（对应 NFR-05 稳定性、NFR-06 权限告知）：
- 钩子被系统静默移除后无法被应用感知（文档明确），因此**不能依赖"钩子异常"信号**。设计上采用**心跳自检**：以用户配置的测试方式（见 §9 待验证项）定期验证钩子是否仍生效；一旦判定失效，提示用户并尝试重装钩子。
  - **回退口径**：若 V-4 实测判定"无法可靠检测"，则退回**周期性重装**策略——按固定间隔（如每 5 分钟）无条件 `UnhookWindowsHookEx` + 重新 `SetWindowsHookEx`，用"宁可多装一次"换取"不会长期处于无钩子状态"。该回退仍满足 NFR-05，代价是极低的周期性开销。
- 钩子回调内只做**最小判定**（比对按键标识），判定结果投递到线程安全队列。

### 3.3 自注入过滤（本设计最易错的一点）

我们自己用 `SendInput` 发出的模拟输入，**会被自己的低级钩子捕获**——因为低级钩子是全局的，`SendInput` 的事件同样进入输入流。若不处理，将出现恶性循环：任务点按 A 键 → 钩子收到 A 键事件 → 若 A 恰是某任务的开关键，就会误触发。

**处理方案**：利用钩子结构体 `KBDLLHOOKSTRUCT` 的 `flags` 字段中的 **`LLKHF_INJECTED`**（键盘）与 `MSLLHOOKSTRUCT` 的 **`LLMHF_INJECTED`**（鼠标）标志——由 `SendInput` 等注入方式产生的输入会被标记为 injected。

> **待核实**：`LLKHF_INJECTED` / `LLMHF_INJECTED` 的确切语义与在 Win10 1809+ 上的可靠行为，需在实现期用实测确认（见 §9 待验证项 V-1）。

**设计口径**：钩子回调**一律忽略 injected 事件**（不作为用户输入处理）。这同时解决了两个问题：① 自身模拟输入不误触发开关；② 不把其他软件的模拟输入当用户操作。

### 3.4 开关按键的"消费"行为（§6.1）

需求 §6.1 要求：开关按键的原始输入"是照常发给系统 还是 被工具吞掉"，需**行为一致**且**逐任务可配**，默认"照常发送"。

**实现方式**：`LowLevelKeyboardProc` 的返回值——"如果挂钩过程处理了消息，它可能会返回**非零值**，以阻止系统将消息传递给钩子链的其余部分或目标窗口过程"。

| 配置 | 钩子回调行为 |
|---|---|
| 照常发送（默认） | 判定为该任务开关键后，仍调用 `CallNextHookEx` 并返回其返回值（事件继续传递） |
| 被吞掉 | 判定为该任务开关键后，返回非零值，**不**调用 `CallNextHookEx`（事件被拦截） |

**按下 / 松开必须成对处理**：低级键盘钩子对**按下（`WM_KEYDOWN` 系）与松开（`WM_KEYUP` 系）分别派发一次回调**。若只吞按下而不吞松开，松开事件会泄漏给系统与链上其他钩子，造成目标程序看到的按键状态不自洽（收到无按下配对的松开），与 §6.1 需求"行为保持一致"相悖。因此吞掉分支的口径是：**该开关键的按下与松开事件，在同一个任务配置下被同等对待**——配置为吞掉则两者都拦，配置为照常则两者都放行。

**鼠标开关键同理**（FR-TOGGLE-01 允许鼠标键作开关键）：`LowLevelMouseProc` 对鼠标按键的按下 / 松开同样分别派发回调，消费口径与键盘一致（吞掉则 down/up 成对拦截）。§3.4 的这张表对**键盘与鼠标两条低级钩子同时适用**，返回值语义相同（非零即拦截）。

**一致性保证**：该行为由任务的配置字段决定，钩子回调对该任务的**每一次**匹配都走同一分支，不引入任何随机/条件分支 → 满足"要么始终生效，要么始终被吞"。

**注意**：文档强调——"应调用 `CallNextHookEx`，除非绝对需要阻止其他应用程序看到通知"。因此"吞掉"分支**仅在用户显式配置时**启用。

**作用域（已裁定）**：该选项为**逐任务配置**，在任务编辑页设置，默认"照常发送"（需求文档 §6.1 / AC-33 口径已对齐）。因此设计中 `ConsumeToggleInput` 作为 §5.1 的**任务字段**成立；设置页**不含**该项。

## 4. 执行模型设计

### 4.1 并行调度模型

需求要求（FR-SEQ-01~05、FR-TAP-04、NFR-03）：任务内命令**并行**、各自**独立频率**、互不影响。

**模型**：**每条命令一个独立的重复节拍器（metronome）**，互不共享计时器。

```
Task (运行中)
 ├── CommandLoop #1  (键盘A·按住)      → 一次性：HoldKey(A)，然后等待任务停止
 ├── CommandLoop #2  (鼠标左键·点按 10次/秒) → 每 100ms：TapMouseButton(Left)
 └── CommandLoop #3  (鼠标移动 2次/秒)  → 每 500ms：MoveMouseAbsolute(x, y)
```

- **点按形态**：循环体 = 执行一次动作 → 等待 `1/频率` 秒 → 重复。
- **按住形态**：循环体 = 执行一次"仅按下" → 不再重复（保持按住），等待任务停止信号。
- **瞬时操作**（FR-TAP-07：鼠标移动、滚轮）：循环体 = 执行一次动作 → 等待 `1/自身频率` 秒 → 重复。

**不使用单一全局调度器**的理由：单调度器上多条命令的排队会引入相互干扰（违反 NFR-03）；独立节拍器天然满足"互不影响"，代价是线程/定时器数量随命令数增长——由 §4.2 的调度策略控制。

### 4.2 定时精度策略（对 NFR-02 的实现）

> **误差带口径的权威定义在需求文档 NFR-02**（1~50 次/秒适用 ±20ms；50 次/秒以上仅要求“实际平均频率 ≥ 配置值 90%”）。下表仅为**便于阅读的摘录**，供本节说明实现手段时参照——区间与判据的定义若有分歧，以需求文档 NFR-02 为准；NFR-02 修订时本节须同步。

频率上限 1000 次/秒 = **1ms 间隔**，这是 Windows 上极难保证精度的区间（系统计时器默认分辨率约 15.6ms）。**这必须提前挑明**：

| 频率区间 | 间隔 | 可达性判断 |
|---|---|---|
| 1~10 次/秒 | 100~1000ms | 轻松达成 ±20ms |
| 10~50 次/秒 | 20~100ms | 可达成，但需提高系统计时器分辨率 |
| 50~1000 次/秒 | 1~20ms | **±20ms 误差带不适用**（带宽大于间隔本身）。需求口径已明确：此区间以"实际平均频率 ≥ 配置值 90%"为验收指标（需求文档 NFR-02） |

**关键矛盾（已裁定）**：NFR-02 的 ±20ms 误差带在 1000 次/秒（1ms）时相对误差达 2000%——该指标在数学上无意义（间隔本身就小于误差带）。**裁定结论**：NFR-02 明确为 **1~50 次/秒适用 ±20ms**；50 次/秒以上改用"实际平均频率 ≥ 配置值 90%"作为验收指标（需求文档 NFR-02 已更新，裁定存档见 §9.1 Q-D1）。

**设计上的应对**：
1. **提高计时器分辨率**：通过 `timeBeginPeriod`（winmm）将系统计时器分辨率提升至 1ms，退出时用 `timeEndPeriod` 还原。**已实测支撑（§9.3 V-2）**：不开时均偏差 5.6~6.2ms（被 15.6ms 时钟粒度拉长），开启后降至微秒级，差异达三个数量级。
2. **重复节拍器用"绝对时间轴"而非"相对睡眠累积"**：以启动时刻为基准，第 n 次动作的目标时刻 = `t0 + n × (1/频率)`，每次计算下一次目标时刻并睡眠到该时刻。**避免累积漂移**（这是精度控制的核心手法：睡眠误差不逐次叠加）。
3. **每个命令一个轻量循环**：优先用**专用线程 + 高精度等待**，而非 `Task.Delay`（后者精度受线程池调度影响）。线程数上限由命令总数决定（见 §4.3）。**实测澄清（§9.3 V-2）**：在 `timeBeginPeriod(1)` 生效前提下，10~200 次/秒区间专用线程与线程池的**精度无可区分**；保留专用线程的理由是**可控性**（线程数不受全局并发影响、可设 `Highest` 优先级、长驻任务不占池线程），非精度。
4. `timeBeginPeriod` 的代价（影响系统能耗，Win10 1809 上生效）——仅在**有任务运行时**调用，全部停止后还原。

### 4.3 并发规模控制

FR-TASK-09 与 Q4 定案："同时运行的任务数量不设上限"，Q2："任务内命令数不设上限"。二者相乘意味着**线程数可能极大**。

**设计口径**：
- 每条命令对应一个逻辑节拍器（§4.1 的模型不变，这是需求语义，不可变）；
- 但**物理承载**（1 命令 = 1 线程 vs 1 命令 = 1 定时器回调）是实现细节，可按实测调整；
- 设计上采用**"逻辑独立、物理复用"**：为高频命令（如 ≥50 次/秒）分配专用线程；低频命令（如 <50 次/秒，间隔 ≥20ms）共享一个调度池——因为它们的抖动容忍度足以被池化。**该阈值划分实测对精度不敏感**（§9.3 V-2：在 `timeBeginPeriod(1)` 生效前提下，10~200 次/秒区间专用线程与调度池精度无可区分），故保留为**工程取舍**（隔离性 / 线程数可控），不因精度理由而改。

> 这里显式标注一个**架构取舍**：物理复用会引入理论上的相互影响，与 NFR-03"互不影响"存在张力。实测表明池化与专用线程在 10~200 次/秒区间精度不可区分（§9.3 V-2），且 20 条并行下达成率 ≥99.3% → **池化在精度维度上安全**；隔离性维度仍按上述阈值划分保障。**验收判据是可测的**（AC-23 / AC-23a / AC-23b），不属于猜测。
>
> **降级口径**：池化被定义为**可选优化**而非精度必需——若实现期证明"1 命令 1 线程"在最大并发下已满足 NFR-02 / AC-23 系列，则不实施池化（回头也符合设计）。池化仅作为"命令数很多且需控制线程数"时的工程手段。

### 4.4 停止与"补发松开"（FR-SEQ-06/07、FR-RUN-05）

**停止流程**（必须做到"立即停止，不得在停止后继续发出"）：
1. 置该任务的**停止标志**（原子变量）；
2. 唤醒所有处于等待中的命令循环，令其**检查标志后立即退出**，不再发出任何事件；
3. 遍历 `InputSimulator` 的"当前按住集合"，补发**松开事件**；
4. 清空该任务的按住集合条目，状态置为"已停止"，通知 UI。

**时序细节**（避免"停止瞬间刚好发出一次动作"）：
- 循环体在**执行动作前**先检查停止标志，执行后再检查一次再进入等待；
- 停止流程先置标志，**再**补发松开——因此不会出现"补发松开之后，某个正在执行的循环又按下"的竞态。

**补发松开的顺序**（FR-TAP-06 明确要求）：
- 组合键按住形态：**主键先松、修饰键后松**（否则修饰键先松会导致主键被当作单键发出）；
- 普通按住：直接松开；
- 多条按住命令的松开顺序**无要求**（不同键之间无依赖），但需保证**同一条组合键内部**的顺序。

## 5. 任务模型

### 5.1 领域对象

```
Task
 ├─ Id            (GUID，内部标识)
 ├─ Name          (string，列表内唯一 → FR-TASK-06)
 ├─ Enabled       (bool → FR-TASK-07)
 ├─ ToggleKey     (KeyBinding，见 §5.2 → FR-TOGGLE-01)
 ├─ ConsumeToggleInput (bool，默认 false → 需求文档 §6.1，逐任务配置)
 ├─ Commands      (List<Command>，不可为空 → FR-SEQ-08)
 └─ RuntimeState  (Stopped | Running，运行期派生，不持久化)

Command (抽象)
 ├─ TapMode       (Tap | Hold，仅键盘/鼠标按键命令适用 → FR-TAP-01)
 ├─ Frequency     (double，次/秒，1~1000 → FR-TAP-04/05)
 ├─ KeyboardKeyCommand  { VirtualKey }                       (FR-CMD-K1)
 ├─ KeyboardComboCommand{ Modifiers[], VirtualKey }          (FR-CMD-K2)
 ├─ MouseMoveCommand    { X, Y }                             (FR-CMD-M1，无 TapMode)
 ├─ MouseButtonCommand  { Button }                           (FR-CMD-M2)
 └─ MouseScrollCommand  { Direction, Notches }               (FR-CMD-M3，无 TapMode)
```

### 5.2 开关按键的表示

`KeyBinding` 需统一表示**键盘键**与**鼠标键**（FR-TOGGLE-01）：

| 来源 | 标识 |
|---|---|
| 键盘 | `VirtualKey`（虚拟键码，如 F6 / Ctrl） |
| 鼠标 | 按键枚举（左/右/中/X1/X2） |

**按键捕获**（FR-TOGGLE-02）通过钩子实现："录制按键"期间，钩子把下一个非 injected 的按键事件上报给 UI 并**消费**掉（避免录制时误触发），界面显示捕获到的键名。**不允许手输**——UI 上只提供捕获按钮，不提供文本框。

### 5.3 保存时校验（对应多条 FR 的"拒绝保存"）

保存是**集中校验点**，全部通过才落盘。校验清单：

| 校验 | 违反时 | 需求 |
|---|---|---|
| 任务名非空且在列表内唯一 | 拒绝 + 提示改名 | FR-TASK-06 |
| 命令集合非空 | 拒绝 | FR-SEQ-08 |
| 点按频率在 1~1000 内 | 拒绝 + 提示 | FR-TAP-05 |
| 开关按键未被其他任务占用 | 拒绝 + 提示冲突 | FR-TOGGLE-05 |
| 开关按键不与**本任务**命令集合内的实体键重叠 | 拒绝 + 提示 | FR-TOGGLE-07 |
| 同一实体键不同时存在"按住"与"点按"两条命令 | 拒绝 + 提示 | FR-SEQ-10 |
| 紧急停止快捷键不与任何任务开关按键冲突 | 拒绝 + 提示 | FR-RUN-03 |

> 校验规则集中在**一个**校验器模块中，UI 保存时调用；避免规则散落在 UI 各处。

**复制任务（FR-TASK-04）的语义**：复制 = 对源任务做**深拷贝**（命令集合逐条新建，不共享引用），生成的新任务名自动加后缀（如"任务名 - 副本"）；副本**必须重新过一遍上述全校验**——特别是任务名唯一性与开关按键占用（副本默认沿用源任务的开关按键，而该键已被源任务占用 → 必须提示用户重新指定）。

## 6. 界面层设计

### 6.1 页面结构

| 界面 | 内容 | 对应需求 |
|---|---|---|
| **任务列表页** | 任务卡片/列表：名称、开关按键、状态标识（运行中/已停止）、启用开关；操作：新建/编辑/复制/删除；**“停止全部任务”按钮**（一键停止所有运行中任务） | FR-TASK-01~04、FR-TOGGLE-04、FR-RUN-04 |
| **任务编辑页** | 任务名、开关按键（捕获）、命令列表（增删改，无排序）；每条命令：类型（下拉）、参数、执行形态（点按/按住/不适用）、频率 | FR-SEQ-01/09、FR-UI-04 |
| **设置页** | 紧急停止快捷键（含**可用性提示**：若该组合已被系统或其他软件占用，提示“该键可能不可用”并引导更换）、开机自启 | FR-RUN-01/02/06、FR-UI-03 |
| **托盘菜单** | 显示主窗口 / 停止全部任务 / 退出 | FR-UI-02 |

**紧急停止快捷键的占用检测（FR-RUN-06 / AC-27）**：设置页提供快捷键配置，用户设定该组合时做**可用性探测**——尝试以 `RegisterHotKey` 试注册该组合，失败（已被其他进程占用）则提示"该键可能不可用"并引导更换；成功则立即注销。即使试注册成功，也在提示中说明该键可能与系统快捷键语义重叠。

> 注：本工具的紧急停止**用低级钩子监听**（§3.2），而非 `RegisterHotKey`——后者会**独占**该组合并使其不再传递给前台程序，与"全局监听且不干扰其他软件"的目标相悖。`RegisterHotKey` 在此**仅作为探测手段**（试注册后立即注销），不用作实际监听。其占用语义需实现期实测确认（§9.2 V-6）。

### 6.2 交互约定（对应需求明文约束）

- **状态实时显示**（FR-TOGGLE-04）：运行状态由 Engine 通过事件通知 UI，UI 更新状态标识并播放过渡动画（NFR-11）。
- **固定取值用选择控件**（FR-UI-04）：命令类型、鼠标按键、滚轮方向、执行形态**一律**使用下拉/单选/按钮，不得出现文本框。
- **删除二次确认**（FR-TASK-03）：删除任务前弹确认对话框。
- **中文界面**（FR-UI-05）：全部界面文案为中文，不引入多语言框架。
- **过渡动画**（NFR-11）：任务启停、保存成功/失败、窗口显隐配过渡动画；动画**不阻塞**主线程；响应系统"减少动画"设置。

### 6.3 系统托盘（WinUI 3 的已知缺口）

WinUI 3 **无内建托盘 API**（§1.3 已述）。方案：

- 通过 P/Invoke 调用 `Shell_NotifyIcon`（`shell32.dll`）添加托盘图标，并在窗口消息循环中处理自定义回调消息；
- 托盘菜单用 Win32 `CreatePopupMenu` / `TrackPopupMenu` 弹出，或用一个轻量 WinUI 弹出层；
- 关闭主窗口时**隐藏而非退出**（FR-UI-01）；退出走托盘菜单（FR-UI-02）。

> **待验证**（§9 V-3）：WinUI 3 应用与 `Shell_NotifyIcon` 的可靠协作方式（特别是消息窗口的建立），需实现期实测。

### 6.4 单实例（NFR-09）

使用命名互斥体（`CreateMutex` + 唯一名称）实现：第二实例启动检测到互斥体已存在时，提示"程序已在运行"并把焦点交给已有实例窗口（AC-30）。

## 7. 配置持久化设计

### 7.1 存储格式与位置

- **位置**：`%APPDATA%\<软件名>\`（FR-CFG-01）；
- **格式**：JSON（人类可读、便于排查；损坏处理的容错路径清晰）；
- **文件**：任务配置与全局设置分文件存放（如 `tasks.json` / `settings.json`），避免一处损坏拖垮全部；
- **写入时机**：保存时**整体写入**（先写临时文件，再原子替换），避免写一半断电导致文件半损坏。

### 7.2 损坏与兼容（FR-CFG-02/03）

| 场景 | 处理 |
|---|---|
| JSON 解析失败 / 结构不符 | **不崩溃**（FR-CFG-02）：捕获异常 → 提示用户 → 加载空配置（可用的最小状态）→ 保留损坏文件为 `.bak` 供排查 |
| 旧版本配置（缺字段/字段增减） | 读取时用**默认值补齐缺失字段**；版本号字段用于识别是否需要迁移；无法兼容时给出**明确提示**（FR-CFG-03） |
| 不提供导入导出 | 界面中**不存在**相关入口（FR-CFG-04） |

### 7.3 日志（FR-CFG-05）

- **记录内容**：任务启动/停止、错误事件（配置读写失败、输入注入失败、钩子异常/失效）；
- **位置**：配置目录下的 `logs\`；**滚动上限**（如保留最近 N 天或 N 个文件），避免无限增长（支撑 NFR-04 内存/磁盘稳定性）；
- 写日志**不得**在钩子回调路径上（违反 §3.2）。

## 8. 关键机制汇总（设计决策 → 需求映射）

| 机制 | 设计决策 | 需求 |
|---|---|---|
| 输入模拟 | `SendInput` 单一出口；维护"当前按住集合" | FR-CMD-*、FR-SEQ-07 |
| 全局监听 | `WH_KEYBOARD_LL`/`WH_MOUSE_LL`；**钩子回调立即返回**；专用消息循环线程；静态回调防 GC 移动 | FR-TOGGLE-06、NFR-05 |
| 自注入过滤 | 钩子忽略 `LLKHF_INJECTED`/`LLMHF_INJECTED` 事件 | §6.1、NFR-07 |
| 开关消费 | 钩子返回值控制：`CallNextHookEx`（照常）vs 非零（吞掉）；逐任务可配、默认照常 | §6.1 |
| 并行执行 | 每条命令一个独立节拍器 | FR-SEQ-01/02 |
| 频率精度 | 绝对时间轴 + `timeBeginPeriod` + 专用线程；避免累积漂移 | NFR-02 |
| 并行隔离 | 高频命令专用线程、低频命令池化（阈值待实测校准） | NFR-03 |
| 停止 | 置标志 → 唤醒退出 → 补发松开；组合键**主键先松** | FR-SEQ-06/07、FR-TAP-06 |
| 紧急停止 | 钩子监听快捷键 → 停止全部任务 | FR-RUN-01~03 |
| 配置 | JSON，`%APPDATA%`，原子写入，容错回退 | FR-CFG-01~03 |
| 单实例 | 命名互斥体 | NFR-09 |
| 托盘 | `Shell_NotifyIcon` + Win32 菜单（WinUI 无内建） | FR-UI-01/02 |
| 原生 UI | WinUI 3 / Fluent，随系统主题 | NFR-10 |
| 动画 | WinUI 过渡动画，响应"减少动画" | NFR-11 |
| 自启 | 注册表 `HKCU\...\Run` | FR-UI-03 |
| 权限 | 清单请求管理员（`requireAdministrator`） | NFR-06、FR-RUN-01 |

> **权限口径（已裁定）**：清单无条件请求管理员，**正常运行路径即提权态**。因此“非管理员启动”不是常态运行场景，而是① 用户明确拒绝 UAC 提权、② 企业策略禁止提权 这两种情况；此时宿主进程根本不会启动，也就无“静默失效”可言。§10 的“非管理员启动时告知”指的是**启动失败路径**——该告知由 **Launcher 启动壳**（§2.2，独立可执行体，清单**不**请求提权）承担：它尝试启动宿主进程，捕获“提权被拒”失败，随即以普通权限弹出明确说明，给出“本工具需管理员权限，否则无法向管理员权限的窗口注入输入”及解决办法（NFR-06、AC-26），而不是让用户面对一个看似正常却处处无效的界面。
>
> **提权失败的判定信号（已实测，见 §9.3 V-7）**：Launcher 用 `Process.Start`（**必须** `UseShellExecute = true`）启动宿主；用户点 UAC「否」时抛 `Win32Exception`，`NativeErrorCode == 1223`（`ERROR_CANCELLED`）。判定以该错误码为准（与"文件缺失(2)""未用 ShellExecute(740)"可明确区分）；成功判定为"未抛异常"，**不得**用宿主退出码。该调用**同步阻塞至用户作答**。

### 9.3 已完成的实测验证（存档）

> 本节存档**已实测闭环**的验证项结论，供追溯；未闭环项仍列于 §9.2。改动本节的结论须以新的实测数据为前提。

**V-2 定时精度实测（已闭环）**

实测环境：Win10 22621，16 逻辑核，.NET 8.0.1，`Stopwatch` 10 MHz；用独立控制台探针（非 WinUI，定时基线不受 UI 框架干扰），测量各档频率下的偏差分布（均偏差 / P50 / P95 / P99 / 最大偏差）与达成率。

| 对照项 | 结果 | 对设计的影响 |
|---|---|---|
| `timeBeginPeriod(1)` 开 vs 关（专用线程） | 开：均偏差 0.001~0.017ms，P99 ≤0.47ms；**关：均偏差 5.6~6.2ms，P95/P99 达 12.5~14ms**（`Thread.Sleep(1)` 被系统 15.6ms 时钟粒度拉长） | **§4.2 第 1 条（必须调 `timeBeginPeriod(1)`）获得实测支撑**：差异达三个数量级 |
| 专用线程 vs 线程池（**均在 `timeBeginPeriod(1)` 生效下**） | 10~200 次/秒区间二者**精度无可区分**（均偏差均为微秒级）；线程池仅在 1 次/秒档出现单次 3.18ms 调度尖峰 | **精度不构成选择专用线程的理由**。保留专用线程是基于**可控性**（线程池线程数受全局并发影响、无法设 `Highest` 优先级、长驻任务占用池线程），此项**实测未推翻也未新增支持** |
| 真实等待策略（>2ms `Sleep(1)` 让出 CPU + 2ms 窗口内自旋）vs 纯自旋 | 200~500 次/秒二者差距在微秒级；纯自旋仅将最坏尖峰压低一档 | **不采用全程自旋**（换取微秒级收益而常驻占满一核不划算）——§4.2 策略成立 |
| 真实 `SendInput` 调用开销 | 各档均偏差 0.054~0.20ms（较纯定时升高约两个数量级，但仍为**亚毫秒**）；P95 ≤1.19ms；频率越高均偏差越小 | `SendInput` 单次调用**不主导抖动**；§4.2 无需为输入调用预留额外时间预算 |
| 多命令并行（5/10/20 条，最高合计 ~3600 次/秒调度压力） | 达成率 ≥99.3%，最大偏差 ≤15ms；500 次/秒档最大偏差 0.78~1.35ms | **并行本身非抖动主因**；§4.3 的并发规模控制成立 |
| 后台干扰（同优先级自旋突发，模拟密集抢占） | 10/50 次/秒无影响；**100~200 次/秒最大偏差恶化至 3.4~7.0ms**（P95/P99 仍 ≤0.74ms，达成率 100%） | 印证「钩子回调须短、须做心跳自检」的必要性（§3.2 / §8）。**注：该数字为同优先级 CPU 抢占的模拟上界，非真实钩子回调的预测值** |

**对 AC-23b 的支撑**：全部组别、全部档位的达成率均 ≥99.3%，远高于「平均频率 ≥90%」的判据 → AC-23b 判据余量充足。

**本次实测未覆盖（不影响上述结论，但限制其外推）**：
- 探针为**控制台**程序；WinUI 3 宿主下的实际精度**未测**（留实现期复测）；
- 干扰模拟为**独立线程自旋突发**，与真实 `WH_KEYBOARD_LL` 回调（运行在安装线程的消息循环上、由系统调用）特征不同，不能替代真实钩子场景的预测；
- 未模拟目标窗口对 `SendInput` 的处理耗时；
- 未覆盖多显示器 / 游戏内 DirectInput、其他进程高负载、节能电源计划等场景。
- 低频池化阈值的具体划分（§4.3 的 ≥50 次/秒分界）**未被本次数据单独校准**——实测表明 10~200 次/秒区间专用线程与线程池精度无可区分，故**阈值划分对精度不敏感**；§4.3 的分界保留为工程取舍（隔离性 / 线程数可控），不因精度理由而改动。

**V-7 Launcher 捕获宿主提权失败实测（已闭环）**

实测环境：Windows 11 22621（`EnableLUA=1`），.NET 8.0.101，x64；用两个临时探针工程——宿主（`requireAdministrator` 清单的最小控制台程序，启动成功即写标记文件）与启动壳（普通权限，`Process.Start` 启动宿主并如实记录异常类型 / `NativeErrorCode` / 返回对象 / 退出码 / 耗时），用完即删。

**测得的失败码与行为**（`ProcessStartInfo.UseShellExecute` 的取值是在**同一宿主目标**下唯一改变的变量）：

| 场景 | `UseShellExecute` | `NativeErrorCode` | 行为 / 时机 | 对设计的影响 |
|---|---|---|---|---|
| 用户在 UAC 对话框点「否」 | `true` | **1223** `ERROR_CANCELLED` | 抛 `Win32Exception`；**`Start()` 同步阻塞至用户作答**（实测约 9.2s，为人工响应时间）；宿主**未启动**（标记文件未生成） | **§8 权限口径获得实测支撑**：Launcher 以捕获该异常作为"提权被拒"的**可靠判定信号**，随后弹出说明（NFR-06、AC-26） |
| 用户批准提权 | `true` | 无异常 | 返回 `Process` 对象；`ExitCode` 为**宿主自身**的退出码，与提权结果无关 | 成功判定不得依赖 `ExitCode`：宿主为常驻 GUI，须以"`Start()` 未抛异常"为成功；「是否已退出」不能用作判据 |
| 目标文件不存在 | `true` | **2** `ERROR_FILE_NOT_FOUND` | 抛 `Win32Exception`，不弹 UAC，立即返回（实测 14ms） | 与 1223 清晰区分；Launcher 可据 `NativeErrorCode` 分流提示文案 |
| **`UseShellExecute = false`（实现失误）** | `false` | **740** `ERROR_ELEVATION_REQUIRED` | 抛 `Win32Exception`，**不弹 UAC、直接失败**（实测 15ms） | ⚠️ **实现约束**：Launcher 启动宿主**必须**设 `UseShellExecute = true`；否则在正常提权机器上会以 740 直接失败，用户看到"启动失败"而非 UAC 提示，AC-26 直接失效 |

**结论**：
1. **判定信号可靠**——「提权被拒」由 `Win32Exception.NativeErrorCode == 1223` 唯一标识，与"文件缺失(2)""未用 ShellExecute(740)"等其他失败码可明确区分，不存在误判。
2. **`Start()` 是同步阻塞调用**——它阻塞至用户对 UAC 作答（批准或拒绝）才返回/抛出。因此 Launcher 的"启动中"状态须覆盖这段可能长达数十秒的等待（不可假设瞬时返回），真实的 UI 反馈应在**启动前**就绪。
3. **成功与失败的分界是"是否抛异常"**，不是退出码——宿主为常驻进程，`ExitCode` 语义不适用。

**本次实测未覆盖（限制结论外推）**：
- 仅测**管理员账户 + `ConsentPromptBehaviorAdmin` 提示态**；**标准用户**（须输入管理员凭据，`ConsentPromptBehaviorUser`）的取消路径**未测**——其 UAC 对话框形态不同，取消码预期同为 1223（`ShellExecuteEx` 层统一返回 `ERROR_CANCELLED`），但**未获本次数据验证**；
- 未测企业策略（`DisableElevation` / 软件限制策略）禁止提权时的返回码——设计上归入"启动失败"分支并提示用户，具体码留实现期实测；
- 未测 UAC 静默提升配置（`ConsentPromptBehaviorAdmin=0`）下的行为——该配置下**不出现对话框**，用户无从"拒绝"，`Start()` 直接成功（本实验中作为对照观察到：返回 `Process`、耗时 306ms）。

> **对实现期的直接约束（源自本次实测）**：Launcher 启动宿主必须 `UseShellExecute = true`；判定逻辑以 `NativeErrorCode` 为准（1223 = 用户取消提权）；成功判定为"未抛异常"，**不得**用 `ExitCode` 或"进程是否退出"判定；启动等待须按"可能阻塞至用户作答"设计。

## 10. 安全与边界

- **权限**：该工具本质上需要管理员权限才能向高完整性窗口注入输入（UIPI 限制，见 §3.1）。清单无条件请求提权（§8），因此正常路径即提权运行；**提权被拒（用户取消 UAC / 策略禁止）导致启动失败时，明确告知用户原因与解决办法**（NFR-06、AC-26），而非静默失效；
- **不干扰**：未运行时/禁用任务不得产生任何输入（NFR-07、AC-25）；实现上确保节拍器只由"启动"流程创建，停止流程彻底销毁；
- **可关闭性**：托盘退出与紧急停止是两条独立路径，均必须能立即终止全部模拟输入（NFR-08、AC-32）；
- **使用边界**：不做反检测设计（N7、§6.3 需求原文的边界声明）。

## 1. 技术选型

### 1.1 选型结论

| 层面 | 选型 | 理由 |
|---|---|---|
| 语言 / 运行时 | **C# / .NET 8**（x64） | 见 §1.2 |
| UI 框架 | **WinUI 3**（Windows App SDK） | 满足 NFR-10 / NFR-11 / §6.4 |
| 平台 API | **Win32 P/Invoke**（User32 / Kernel32） | 输入模拟、全局钩子、坐标 |
| 配置格式 | **JSON**（`System.Text.Json`） | 见 §7.1 |
| 分发形态 | 非打包 + 宿主单文件自包含（§1.4） |

### 1.2 语言选型的理由

本项目的性能瓶颈**不在语言本身**，而在一条架构约束（见 §3.2：钩子回调必须立即返回）。C# 完全能守住该约束，而它在 UI 开发效率上显著优于 C++，且 WinUI 3 对 C# 是一等公民支持。

- **不选 C++**：能力上够，但对本项目是过度投入——GUI 开发成本高，而收益（更低延迟）在需求口径（NFR-01 ≤50ms、NFR-02 ±20ms）内体现不出来。
- **不选 Rust**：WinUI 3 无官方 Rust 绑定，选它就得放弃原生 UI 栈，与 NFR-10（Windows 原生视觉风格）直接冲突。
- **不选 WPF / WinForms**：属 .NET 上一代 UI 技术，控件外观非 Windows 11 原生，与 NFR-10 冲突。

### 1.3 WinUI 3 的适配性（依据）

WinUI 3 官方定位："用于构建新的 Windows 桌面应用程序的推荐原生 UI 框架"，"可用于创建在 **Windows 10 版本 1809（内部版本 17763）** 及更高版本上运行的现代、美观和响应式桌面体验"，且 "Windows shell 及其内置应用的某些部分是使用 WinUI 生成的"。

| 需求 | WinUI 3 如何满足 |
|---|---|
| NFR-10 原生风格 + 简约 | WinUI 3 即 Windows 自身的设计语言（Fluent），控件与系统主题（深/浅色）自动同步 |
| NFR-11 过渡动画 + 尊重"减少动画" | WinUI 3 动画系统基于系统合成器，随系统辅助功能设置自动减弱 |
| §6.4 最低 Win10 1809 | 与 WinUI 3 官方支持线完全一致 |
| FR-UI-04 固定取值用选择控件 | ComboBox / RadioButtons / ToggleButton 等原生控件直接覆盖 |

**待评审确认的取舍**：WinUI 3 应用**不支持系统托盘**（`Shell_NotifyIcon` 无 WinUI 封装）。因此托盘（FR-UI-01/02）需通过 **Win32 互操作**实现——自己调用 `Shell_NotifyIcon` 并处理其回调消息。这是本选型唯一的明显代价，方案见 §6.3。

### 1.4 分发形态（已确定）

- **打包方式：非打包（unpackaged）**。排除 MSIX 的理由有一条**硬冲突**与一条**补充冲突**（均已按官方口径修正）：

  **① 提权与包模型直接冲突（硬冲突，决定性理由）**。官方把「应用总是以提升的权限运行」列为**打包前必须解决的阻碍项**：*"Your application always runs with elevated security privileges. … requiring your application to run elevated means that it won't run correctly for standard users."*（`desktop-to-uwp-prepare`）；同页给出硬判据——需要提权的应用**不会被 Microsoft Store 接收**。这与已裁定的「宿主进程整体提权」（NFR-06 / §8 / Q-D3）**正面冲突**。注意：`AllowElevation` / `appExecutionAlias` 之类解决的是「如何启动应用」，不是「进程以何种令牌运行」，**无法**绕开该冲突。本工具的输入注入必须对管理员权限窗口生效，提权是功能前提而非偏好。

  **② `%APPDATA%` 写入路径（补充冲突；原口径已修正）**。打包应用写入 AppData 会被重定向到 per-user/per-app 私有位置（读取时与真实路径合并显示）；官方另提供关闭该行为的受限能力 `unvirtualizedResources` + `FileSystemWriteVirtualization=disabled`。**原文档「`%APPDATA%` 被重定向到包容器、路径不再成立」的表述过宽**——该重定向在《Behind the scenes》中被明确限定为 *"This section applies only to virtualized apps."*，即 **appContainer（`TrustLevel="appContainer"`）应用；full-trust（`mediumIL`）打包应用不适用**。但《Flexible virtualization》以 **"Default MSIX behavior"** 为标题、**未加此限定**地列出同一行为。**两页官方表述不一致，本文不自行裁定倾向哪一方**；取对非打包有利的保守解读：若选打包，须显式声明 `unvirtualizedResources` 才能确保 FR-CFG-01 的 `%APPDATA%` 语义，而该能力需额外受限能力声明与商店审批。

  ② 的代价：修复需**回头修改已冻结需求或已裁定项**；①更是与本项目功能前提不可调和。两者合计的代价远大于非打包的部署便利损失。非打包亦更贴合本工具「绿色常驻」的定位。
- **宿主可执行体：单文件自包含（self-contained single-file）**。不依赖目标机预装 .NET 8 运行时，也不依赖预装 Windows App SDK 运行时；拷贝即用。代价是体积增大——**实测 x64 发布产物约 217 MB**（§9.3），高于早期“约 150MB+”的估值（该估值未计入 Windows App SDK 运行时负载）。对本工具“必须提权运行、多一步安装就多一道障碍”的场景，该代价可接受。
- **两个可执行体，职责分离（见 §2.2）**：外层 `Launcher.exe`（普通权限，清单**不**请求提权）负责启动内层并捕获提权失败；内层 `鼠标键盘辅助.exe`（清单 `requireAdministrator`）为业务宿主。**两层不能合并为单个 EXE 的双模式**：若同一 EXE 带 `requireAdministrator` 清单，外壳自身也会被强制提权，从而丧失“以普通权限弹出提权失败提示”的能力（AC-26）。
- **应用图标：全产品单一图标源 `src/Host/Assets/AppIcon.ico`**。该文件承担三处用途，改一处全部生效：
  1. **窗口图标（标题栏 + 任务栏按钮，二者同源）**——`MainWindow` 的 `ApplyWindowIcon()`：从宿主 exe 的 **PE 资源**取图标（`TrayIcon.LoadIcon`，与托盘同一处实现），再经 `WM_SETICON` 分别按 `ICON_SMALL` / `ICON_BIG` 挂到窗口上。
  2. **托盘图标**——`TrayIcon` 构造函数，同样调 `TrayIcon.LoadIcon`；与条目 1 共用一处实现，保证两者不会各走一条路径而出现「托盘变了、任务栏没变」。
  3. **exe 文件图标**（资源管理器所见）——两个工程的 `ApplicationIcon` 属性：Host 用 `Assets\AppIcon.ico`，Launcher 用 `..\Host\Assets\AppIcon.ico` 跨项目引同一文件（用户视角 `Launcher.exe` 与宿主是同一软件，故不另设图标）。

  **窗口图标不按文件路径取**（不用 `AppWindow.SetIcon("Assets/AppIcon.ico")`，也不在 `MainWindow.xaml` 里写 `TitleBar.IconSource`）：发布形态是单文件自包含，**产物目录里没有 `Assets\` 文件夹**（实测产物仅一个 exe + pdb），任何指向该目录的相对路径在发布产物里都解析不到，窗口会退回 WinUI 默认图标——曾经的缺陷现象「托盘图标换了、任务栏按钮没换」即源于此（托盘走 exe 的 PE 资源，不受影响）。改走 PE 资源后本条不依赖任何随包文件。

  **尺寸**：`ExtractIcon` 只返回图标组的第一帧（32×32），而单文件发布下 `LoadImage` 的 `LR_LOADFROMFILE` 取不到散装文件（实测返回 0），拿不到原生 16×16 那一帧；故两档共用同一个 32×32 句柄，由系统降采样——可用的近似。

  **句柄归属**：`WM_SETICON` 后窗口即持有自己的引用（实测：销毁原句柄后 `WM_GETICON` 回读仍非 0），故窗口侧在挂上后立即 `DestroyIcon`，不销毁即 GDI 泄漏；托盘侧句柄由 `TrayIcon.Dispose` 释放。两处各自取句柄，互不别名。

  **取图标失败不退启动**：退回系统默认图标（`IDI_APPLICATION`），与托盘同一口径。

  **`ApplicationIcon` 是纯编译期属性**（写进 PE 的 `RT_ICON` / `RT_GROUP_ICON` 资源），**不参与 publish 的复制管线**——因此 Host 让它指向 `Assets\` 不会触发 `Host.csproj` 所述的三重纳入冲突（那条链路的成员是「SDK None 通配 / WinUI Content 通配 / 显式 Content 复制项」，`ApplicationIcon` 不在其中：它既不进 `ResolvedFileToPublish`，也不改上述任一项的元数据）。

  **`Assets\` 只准放 `AppIcon.ico` 一条**（理由见 `Host.csproj` 内注释）——新增本图标（或任何文件）到该目录都会重新引入通配符条件匹配问题，故本方案**不新增任何文件**，仅原地替换既有 ico。
- 具体 .NET 版本补丁与 Windows App SDK 版本号已定：Windows App SDK **2.5.1**（写死，不用通配符）；TFM `net8.0-windows10.0.22621.0`。完整构建配方与三处工具链约束见 §9.3。

> 上述选择只影响安装与部署，**不影响 §2 的架构判断**（模块划分、进程/线程模型、输入层设计三者与打包方式无关）。

```
│  应用核心（Engine）                           │

│  │ 任务仓库  │ │ 任务调度  │ │ 配置持久化    │ │
│  │ Registry │ │ Scheduler│ │ ConfigStore  │ │
│  └──────────┘ └────┬─────┘ └──────────────┘ │
```

### 2.2 模块职责与依赖

| 模块 | 职责 | 依赖 | 对应需求 |
|---|---|---|---|
| **UI 层** | 呈现与交互：任务增删改、按键捕获、状态显示、设置页、托盘 | Engine | FR-TASK-01~06、FR-TOGGLE-02/04、FR-UI-01~05 |
| **任务仓库 Registry** | 内存中的任务集合、唯一性校验、冲突校验、状态机（运行/停止/启用/禁用） | — | FR-TASK-06~09、FR-TOGGLE-05/07、FR-SEQ-08/10、NFR-09 |
| **任务调度 Scheduler** | 任务启停、每条命令的独立定时循环、并行编排、停止时补发松开 | InputSimulator | FR-SEQ-01~07、FR-TAP-*、NFR-01/02/03 |
| **配置持久化 ConfigStore** | 配置读写、损坏回退、版本兼容 | Registry | FR-CFG-01~05 |
| **全局钩子 HookService** | 监听键盘/鼠标低级事件，识别开关按键与紧急停止 | —（向上投递事件） | FR-TOGGLE-06、FR-RUN-01、§6.1 |
| **组合根 HostFacade** | **进程内的装配与协调中心**（Engine 层）：持有并接线 Registry / Scheduler / ConfigStore / HookService / InputSimulator；订阅 `ToggleRequested` → 查表得任务 → `Scheduler.Toggle`；配置变更后重建 `ToggleSnapshot` 并推送；对外暴露面板态（`RunStateChanged`）。**不承载业务规则**（校验在 TaskValidator、调度在 Scheduler），只负责“谁认识谁”与“谁驱动谁” | Registry / Scheduler / ConfigStore / HookService / InputSimulator | FR-RUN-01~05、FR-TOGGLE-06、FR-CFG-01~03、NFR-09 |
| **启动壳 Launcher** | 独立可执行体 `Launcher.exe`（**普通权限**，清单**不**请求提权）：启动宿主并捕获提权被拒，随即告知用户（AC-26）。不承载业务逻辑。形态：`OutputType=WinExe`（无控制台窗口） + Win32 原生 `MessageBox` 提示（不引入 WinForms/WPF）；与宿主同为单文件自包含发布（§1.4） | — | NFR-06、AC-26 |
| **日志 Logger** | 记录任务启停与错误事件 | — | FR-CFG-05 |

**依赖方向**：UI → Engine → Input。Input 层不反向依赖 Engine（它只投递事件，由 Engine 订阅），避免循环依赖。**Launcher 独立于上述三层**：它不参与运行时架构，只在启动阶段存在（详见 §8 权限口径）。

**组合根的落点（S9 裁定）**：装配代码落 `src/Host/Engine/HostFacade.cs`（Engine 层内），**不另建 `AppServices.cs` 之类的独立装配文件**。理由是 `Ui → Engine → Input` 的单向依赖必须由某个 **Engine 侧**类型来缝合——把装配塞进 UI 层会让 UI 直接 new 出 Input 层对象、依赖方向被绕过；把装配塞进 Input 层则使 Input 反向认识 Engine，直接违规。Engine 层内是唯一同时看得见两侧且方向合法的位置。

### 2.3 数据流（一次开关键点按的全过程）

```
用户按键
  → HookService 钩子回调（钩子线程）
      ① 判定：是否匹配某个已启用任务的开关按键？
      ② 立即投递事件到事件队列，钩子回调随即返回（不在此处执行任何输入模拟）
  → Engine（工作线程）从队列取出事件
      ③ 切换任务状态：停止 → 启动 / 运行 → 停止
      ④ 若为"启动"：为任务的每条命令创建定时循环（并行）
         若为"停止"：终止全部循环，补发"按住中"按键的松开事件
  → InputSimulator 在工作线程上调用 SendInput 发出事件
  → UI 通过数据绑定/事件收到状态变更通知，更新显示（FR-TOGGLE-04）
```

**关键点**：第 ② 步的"立即返回"是整个架构的安全绳（依据见 §3.2）。

## 3. 输入层设计

### 3.1 输入模拟：SendInput

选用 Win32 `SendInput`（`user32.dll`）作为唯一的输入模拟出口，不使用 `keybd_event` / `mouse_event`（旧式 API，微软文档已将其列为被 `SendInput` 取代，且日志钩子 API 已废弃并"强烈建议改为调用 SendInput"）。

`SendInput` 的语义要点（决定实现细节）：
- 事件**串行插入**输入流，与用户物理输入或其他调用产生的输入**不会交错**；
- 受 **UIPI** 约束："仅允许应用程序将输入注入到完整性级别相等或更低级别的应用程序"——这解释了 FR-RUN-01 与 NFR-06 为何需要管理员权限；
- **不会重置键盘当前状态**："调用函数时已按下的任何键都可能会干扰此函数生成的事件"，文档建议用 `GetAsyncKeyState` 检查并按需纠正。

**设计定位**：`InputSimulator` 是**唯一**向上暴露语义化注入方法的地方；但**真正的 `SendInput` 调用只存在于宿主侧的一个薄适配器**（`SendInputSink`，实现 `IInputSink`）——这一分层使决策逻辑可被单测穷举（§13.1）。

`IInputSink`（Core，纯逻辑层的注入出口）每个方法返回**本次实际注入的事件数**（同 `SendInput` 口径），并提供 `LastInjectionError`（最近一次注入的 Win32 错误码，`0` = 无失败 / 无可用原因）作为失败类型的诊断线索——**成败一律以返回事件数为准**，`LastInjectionError` 只用于把“为什么失败”写进日志，且并发下可能被覆盖，调用方须紧接着读。

向上暴露语义化方法：

```
TapKey(vk)                  // 按下 + 松开（点按）
HoldKey(vk, owner)          // 仅按下
ReleaseKey(vk, owner)       // 仅松开
TapMouseButton(button)
HoldMouseButton(button, owner)
ReleaseMouseButton(button, owner)
MoveMouseAbsolute(x, y)     // 绝对坐标
ScrollWheel(direction, notches)
TapCombo(modifiers, vk)     // 修饰键↓ → 主键↓↑ → 修饰键↑
HoldCombo(modifiers, vk, owner)    // 修饰键↓ → 主键↓（保持）
ReleaseAll(owner)           // 按属主补发松开（§3.1.3 唯一入口）
ReleaseAllAll()             // 释放全部属主（紧急停止 / 退出）
```

**`owner` 口径**：持有类方法（`Hold*` / `Release*`）都带一个 `owner` 参数，取值是任务的 `Guid`（`TaskDefinition.Id`）。`Guid.Empty` 保留为“非任务属主”（不属于任何任务的临时按住）。**点按类方法（`Tap*`）不带 `owner`**——它们不走引用计数（§3.1.1），也不进按住表。

**注入键码口径（归一）**：修饰键（Ctrl / Shift / Alt / Win）在**按下侧与松开侧统一只注入左右归一后的代表键**（左 Ctrl 等）。左右修饰键在物理键盘上是两个不同虚拟键码，但 §3.1.1 已把它们当作同一个实体条目入表；若按下注入原始键而松开注入归一键，就会出现“按右 Ctrl、松左 Ctrl”——右 Ctrl 永久卡在按下状态。归一只为对齐**同一个实体条目**；`Tap*` 不参与此口径（它不进表，按配置原样注入）。

`InputSimulator` 内部维护一个**"当前按住集合"**（按下的键/键鼠按钮的集合），这是 FR-SEQ-07 / FR-RUN-05 补发松开的**唯一权威来源**——不靠遍历命令反推，而是记录实际按下、尚未松开的事件。

#### 3.1.1 按住集合的作用域与引用计数（已裁定）

**按住集合是全局唯一的一张表**（不是每任务一张），原因是**物理键盘只有一份状态**：两个任务分别按住 A 和 B 时，松开 A 不能连带松开 B；而两个任务**都**按住 A 时，其中一个停止也不得松开 A——后者的键仍在按着。

因此每个条目带**引用计数**：

```
按住条目 = { 物理键/鼠标按钮, 引用计数 N, 属主集合（哪些任务持有） }
```

- 按下：条目不存在则新建（`N=1`）；已存在则 `N++`，**不再向系统重复发按下事件**（已按下状态重复 SendInput 按下是无效动作，且会让上层误判实际状态）；
- 释放：`N--`；仅当 **`N == 0`** 时才真正发出松开事件并从表中移除；
- 属主集合用于**按任务解除**（任务停止时只释放它自己持有的引用），无需知道其他任务按了什么。

> **组合键的原子性**：`HoldCombo` 的修饰键与主键同属**一个**条目的持有单元——任务停止时两者一起减引用、一起按「主键先松、修饰键后松」的顺序补发（§4.4），不得拆开。

**为什么不用简单的 `HashSet`**：无计数的集合在"两任务按住同一键"时会提前松开，直接违反 FR-SEQ-07（按键卡住的反面，变成"任务仍在运行但键被松掉"）。引用计数使两张语义都被满足。

#### 3.1.2 `SendInput` 失败的处理（已裁定）

`SendInput` 受 **UIPI** 约束（§3.1），向**更高完整性级别**的窗口注入会被静默丢弃——它返回实际插入的事件数，失败时**可能小于请求数甚至为 0，而不抛异常**。

**裁定：不静默忽略，也不上抛终止任务。**

1. **检查返回值**——`SendInput` 返回实际注入的事件数，与请求数不符即视为**注入失败**；
2. **记日志**（§7.3 已列"输入注入失败"为日志内容，FR-CFG-05）——记录失败类型与目标事件，但**不走钩子回调路径**（§3.2）；
3. **不中断任务**——任务继续运行并**继续尝试**。理由是失败往往是**暂时**的（目标窗口当时是提升态、稍后切走即恢复），终止任务会让用户面对一个"莫名其妙停了"的工具；而上报 UI 拉活挂弹窗又会在高频命令下变成刷屏。

**降频约束**：同一命令的注入失败日志**按时间窗口聚合**（如每分钟最多一条），避免高频失败刷爆日志文件、拖垮 §4 的时间轴（NFR-04）。

> **边界（与 NFR-06 的关系）**：本工具自身要求管理员权限（§10），正常路径下不触发 UIPI；此处处理的是**残留场景**（目标窗口属于**更高**完整性级别，如系统保护进程 / 部分安全软件界面）。**不做**反检测或绕过 UIPI 的设计。

#### 3.1.3 补发松开的唯一入口（已裁定）

补发松开有**三个触发源**，但**只走一条实现路径**：

| 触发源 | 需求 |
|---|---|
| 任务停止（开关点按 / 列表页停止按钮） | FR-SEQ-06/07、FR-RUN-04 |
| 紧急停止快捷键 | FR-RUN-01、NFR-08、AC-32 |
| 软件退出 | FR-RUN-05、AC-32 |

**唯一入口**：`InputSimulator.ReleaseAll(owner)`——按属主解除引用计数，`N` 归零的条目才真正发松开，顺序遵守 §4.4（组合键主键先松）。

- 单任务停止 → `ReleaseAll(该任务)`；
- 紧急停止 / 退出 / 停止全部 → 遍历全部属主逐个 `ReleaseAll`（外层可提供 `ReleaseAllAll()`，内部仍走同一条减引用逻辑）。

> **为何强制单一入口**：三个触发源若各自写一套松开逻辑，会重复踩"引用计数漏减"与"组合键顺序颠倒"两个坑；合并后，**"松开键"这件事只有一处代码**，新增触发源时只需调用同一个方法。


> **已知限制（跨任务点按 / 按住交互）**：按住表是**全局唯一一张**（§3.1.1），但**点按链路（`Tap*`）不进表**（§3.1:163），故 `Tap*` 与引用计数**互不影响**。由此产生的边界行为：
> - 任务 A 按住某修饰键（表中 `N>0`）期间，任务 B 对同一实体键的**点按**仍会原样发出完整的 `down`/`up` 序列——它不查表、不增不减计数。
> - 因此 B 的 `up` 可能**提前抵消** A 的按住效果（物理按键被抬起），是**已知且接受**的语义，**不属于缺陷**。
>
> **口径来源**：需求 FR-SEQ-10 只约束**单个任务内**的命令顺序，**未规定跨任务口径**；本限制按"与 §3.1:163 自洽"取舍落定为 `Tap*` 完全旁路引用计数（用户裁定 2026-10-08）。
> **若要改为跨任务隔离记账**（`Tap*` 也进表 / 按任务分表），需先修订 FR-SEQ-10，本设计**不自行发明**该口径。

### 3.2 全局钩子：钩子回调短小化（架构硬约束）

选用 `SetWindowsHookEx(WH_KEYBOARD_LL / WH_MOUSE_LL)` 实现全局监听（FR-TOGGLE-06）。微软文档给出三条必须遵守的约束：

| 文档原文要点 | 对本设计的要求 |
|---|---|
| "挂钩过程处理消息的时间应短于 `LowLevelHooksTimeout`"；"如果挂钩过程超时……在 Windows 7 及更高版本上，挂钩以**静默方式删除**，无需调用。**应用程序无法知道挂钩是否已删除**" | 钩子回调**绝不做重活**——不调 `SendInput`、不写文件、不做 UI 更新 |
| "安装挂钩的线程**必须具有消息循环**" | 钩子安装在一个**专用线程**上，该线程运行消息泵 |
| "应在将工作传递给工作线程、然后**立即返回**的专用线程上运行挂钩" | 即上面的专用线程；判定后把事件投递出去就走 |

**另外两条必须处理的约束**：
- `WH_KEYBOARD_LL` / `WH_MOUSE_LL` **仅支持全局范围**（文档明列）；
- "**全局挂钩函数必须位于库（DLL）中**"——低层钩子（LL 型）的特殊之处在于：钩子回调在安装它的线程上下文中被调用，**不注入其他进程**（文档明确："WH_KEYBOARD_LL 挂钩不会注入到另一个进程中。相反，上下文将切换回安装挂钩的进程"）。因此本设计**无需额外的独立 DLL**，回调可留在主程序集内——但**必须保证回调不被 GC 移动**（文档："在 .NET 应用中，必须确保垃圾回收器不会移动回调（否则你的应用会因 ExecutionEngineException 而崩溃）。执行此操作的一种方法是将回调设置为类的静态方法"）→ 回调实现为**静态方法**并持有委托引用。

**超时风险的应对**（对应 NFR-05 稳定性、NFR-06 权限告知）：
- 钩子被系统静默移除后无法被应用感知（文档明确），因此**不能依赖"钩子异常"信号**。设计上采用**心跳自检**：以用户配置的测试方式（见 §9 待验证项）定期验证钩子是否仍生效；一旦判定失效，提示用户并尝试重装钩子。
  - **回退口径**：若 V-4 实测判定"无法可靠检测"，则退回**周期性重装**策略——按固定间隔（如每 5 分钟）无条件 `UnhookWindowsHookEx` + 重新 `SetWindowsHookEx`，用"宁可多装一次"换取"不会长期处于无钩子状态"。该回退仍满足 NFR-05，代价是极低的周期性开销。
- 钩子回调内只做**最小判定**（比对按键标识），判定结果投递到线程安全队列。

**回调返回值的即时性约束（实现要点）**：钩子的返回值是**同步且强制**的——系统拿到返回值后才决定事件是否继续传递，回调**不能"先返回、稍后由消费者决定"**。因此凡是影响返回值的信息（最典型的是 §3.4 的"照常发送 / 吞掉"），**必须在回调内以廉价方式当场读出**，不能经由所投递的队列往返获取。

由此，钩子侧的按键判定与消费决策**读的是一张预计算快照**（见 §3.4"快照机制"），而非实时遍历任务列表：回调内只做「按键标识 → 快照查表 → 读一个布尔位」三件事，与"最小判定"约束一致。任务列表的任何变更由拥有者在回调之外重建快照并整体替换，回调侧永不触碰任务模型、调度器或配置存储。

### 3.3 自注入过滤（本设计最易错的一点）

我们自己用 `SendInput` 发出的模拟输入，**会被自己的低级钩子捕获**——因为低级钩子是全局的，`SendInput` 的事件同样进入输入流。若不处理，将出现恶性循环：任务点按 A 键 → 钩子收到 A 键事件 → 若 A 恰是某任务的开关键，就会误触发。

**处理方案**：利用钩子结构体 `KBDLLHOOKSTRUCT` 的 `flags` 字段中的 **`LLKHF_INJECTED`**（键盘）与 `MSLLHOOKSTRUCT` 的 **`LLMHF_INJECTED`**（鼠标）标志——由 `SendInput` 等注入方式产生的输入会被标记为 injected。

> **待核实**：`LLKHF_INJECTED` / `LLMHF_INJECTED` 的确切语义与在 Win10 1809+ 上的可靠行为，需在实现期用实测确认（见 §9 待验证项 V-1）。

**设计口径**：钩子回调**一律忽略 injected 事件**（不作为用户输入处理）。这同时解决了两个问题：① 自身模拟输入不误触发开关；② 不把其他软件的模拟输入当用户操作。

### 3.4 开关按键的"消费"行为（§6.1）

需求 §6.1 要求：开关按键的原始输入"是照常发给系统 还是 被工具吞掉"，需**行为一致**且**逐任务可配**，默认"照常发送"。

**实现方式**：`LowLevelKeyboardProc` 的返回值——"如果挂钩过程处理了消息，它可能会返回**非零值**，以阻止系统将消息传递给钩子链的其余部分或目标窗口过程"。

| 配置 | 钩子回调行为 |
|---|---|
| 照常发送（默认） | 判定为该任务开关键后，仍调用 `CallNextHookEx` 并返回其返回值（事件继续传递） |
| 被吞掉 | 判定为该任务开关键后，返回非零值，**不**调用 `CallNextHookEx`（事件被拦截） |

**按下 / 松开必须成对处理**：低级键盘钩子对**按下（`WM_KEYDOWN` 系）与松开（`WM_KEYUP` 系）分别派发一次回调**。若只吞按下而不吞松开，松开事件会泄漏给系统与链上其他钩子，造成目标程序看到的按键状态不自洽（收到无按下配对的松开），与 §6.1 需求"行为保持一致"相悖。因此吞掉分支的口径是：**该开关键的按下与松开事件，在同一个任务配置下被同等对待**——配置为吞掉则两者都拦，配置为照常则两者都放行。

**鼠标开关键同理**（FR-TOGGLE-01 允许鼠标键作开关键）：`LowLevelMouseProc` 对鼠标按键的按下 / 松开同样分别派发回调，消费口径与键盘一致（吞掉则 down/up 成对拦截）。§3.4 的这张表对**键盘与鼠标两条低级钩子同时适用**，返回值语义相同（非零即拦截）。

**一致性保证**：该行为由任务的配置字段决定，钩子回调对该任务的**每一次**匹配都走同一分支，不引入任何随机/条件分支 → 满足"要么始终生效，要么始终被吞"。

**注意**：文档强调——"应调用 `CallNextHookEx`，除非绝对需要阻止其他应用程序看到通知"。因此"吞掉"分支**仅在用户显式配置时**启用。

**作用域（已裁定）**：该选项为**逐任务配置**，在任务编辑页设置，默认"照常发送"（需求文档 §6.1 / AC-33 口径已对齐）。因此设计中 `ConsumeToggleInput` 作为 §5.1 的**任务字段**成立；设置页**不含**该项。

#### 3.4.1 快照机制（实现要点，本节补充设计）

§3.2 的"回调返回值即时性约束"决定了：**吞掉与否必须在钩子回调内当场判定**，不能等到队列消费者。任务列表却是可变且可能很长的——回调里遍历任务列表会让回调变重，直接违反 §3.2 的"最小判定"。

**机制：不可变快照 + 指针整体替换（pointer swap）**。

```
快照 = 不可变条目表： 主键(族归一后) → { 修饰键族集合, bool consume, bool IsCombo }
```

- **构建**（回调之外，由配置拥有者触发）：遍历当前任务列表，取每个**启用**任务的 `ToggleKey`，按 §3.1 的族归一口径归一（用 `KeyCatalog.RepresentativeOfFamily`，与按住表同源），填入 `consume = 该任务. ConsumeToggleInput` 与 `modifiers = 该任务.ToggleKey.Modifiers`（同样归一）。构建完成后**整体替换**快照引用。
- **读取**（回调之内）：一次字典查找 + 一次常量级比对（修饰键集合是组合形态才非空，单键与鼠标键形态**不做任何额外判定**），无锁、无分配、不触碰任务模型。
- **并发安全**：快照**发布后不再修改**（不可变），替换是单一引用的原子写（`Volatile.Write` / `Interlocked.Exchange`）；回调侧用 `Volatile.Read` 取当前引用。因此回调**永不阻塞**（不取任何锁），也就不可能因等待锁而逼近 `LowLevelHooksTimeout`。
- **同键冲突**：多个任务共用同一开关键、且 `ConsumeToggleInput` 取值不一致时，采用**确定性合并**（"任一要求吞掉即吞掉"）——因为吞掉是更保守的一侧（截断事件可见性），且 §3.4:270 要求同一配置每次走同一分支：合并结果与遍历顺序无关，天然满足"不引入随机分支"。
- **同主键不同修饰集**（同一条目的细化口径）：字典键是**主键**，修饰键族集合进值。
  同主键、修饰集不同的两个绑定**在保存期已被拒绝**（FR-TOGGLE-05 取**主键**口径，
  即 `F8` / `Ctrl+F8` / `Alt+F8` 三者互斥），实现为 `TaskValidator.IsSameToggleKey`，
  故下列合并**在生产路径不可达**。

  **为何同主键一律拒绝（而不是允许共存后靠合并兼容）**：两个理由，第二个是结构性的——
  1. 主键相同即会在同一次点按里命中两条条目，**同一次输入启停两个任务**，用户无法预期；
  2. 修饰键按下状态的**漏同步**（见本节末“无重同步路径”）会把本应“需要 Ctrl”的组合
     降级为裸键命中。若允许 `Ctrl+F8` 与 `Alt+F8` 共存，一旦修饰键状态漏掉，
     两者就退化成两个不可区分的 `F8`——冲突被从一个“保存时看得见”的枚举，
     转成一个“运行中偶发”的幽灵。故不得留同主键的合法绑定。
  后一条也是驳回“按完整绑定判等、允许 `Ctrl+F8` 与 `Alt+F8` 共存”这一方案的理由。

  **防御路径（手改坏配置的自愈）**：字典仍不能假设“一个主键一个条目”——
  校验器拦不住绕过 UI 直接改配置文件。因此同主键条目仍做**确定性合并**
  （`ToggleEntry.Merge`）：修饰集取**并集**，`consume` 取或。
  取并集而非替换，是为了让两个原修饰组合都仍有可命中的组合
  （`Ctrl+Alt+F8` 同时满足两者），没有任何一方被静默吞掉——
  没有它，后一个任务会静默覆盖前一个，且“哪个胜出”取决于任务在列表里的顺序，
  用户看到的是“开关时灵时不灵”而无从归因。
- **组合命中判定**（`IsCombo` 为真时）：命中 = 主键命中 **且** 条目的修饰键族集合 ⊆ 当前按下的修饰键族集合（逐族包含，非集合相等——多按了修饰键仍命中）。修饰键族集合在钩子侧维护（键盘路径），鼠标键不参与该判定（组合形态仅键盘）。

**为什么不用加锁的共享字典**：回调持锁读取会引入"回调等锁"的路径——锁若被配置写入方长时间持有，回调即超时，钩子被系统静默摘除（§3.2）。指针替换把**写侧**的复杂度（可慢）与**读侧**的代价（必须极快）彻底解耦。

**归属（分层）**：快照由**拥有者**在钩子之外重建并推送给钩子服务；钩子服务（Input 层）只持有与读取，**不认识任务模型、不依赖调度器**（维护 `Ui → Engine → Input` 的单向依赖，§2.1）。触发重建的时机（启动、配置变更、任务启停不改变开关键故不需要）由拥有者决定，不在本层。

<a id="无重同步路径"></a>
**无重同步路径（修饰键族状态的兜底对账）**

组合命中的前置条件是“修饰键族集合 ⊆ 当前按下族集合”，而该集合**只在钩子回调里增删**（`TrackModifier`）。于是有一个结构性的口子：**key-up 未必总能收到**——UAC 提权确认、安全桌面切换、进程被挂起期间，`WH_KEYBOARD_LL` 回调收不到事件。一旦漏收某个 key-up，该族计数永不归零，从此**所有需要该修饰键的组合开关键永久失灵**，且用户完全无从知晓（没有任何提示，也没有任何界面能反映这个内部状态）。

**做法**：每次键盘事件回调里，在 `TrackModifier`（维护）之后、查表（命中判定）之前，插入一次**对账**（`ReconcileModifierFamilies`）：逐个枚举**已记账的族**，用 `GetAsyncKeyState` 核实该族的左右两键是否**真的还有按着的**；任何一个都没按着就地移除该族。这样做的效果是把“**永久的**错误状态”降级为“**最多错到下一次键盘事件**”。

**宽限期（本设计的必要条件，2026-10-10 修）**：`GetAsyncKeyState` 读的是**全局异步键盘状态**，与低层钩子的事件队列是**两条独立通路** —— 回调是在事件被投递时执行的，此刻该按键的物理状态**未必**已反映到 `GetAsyncKeyState`。实测证据：按下 LeftCtrl 的瞬间读出 `vk=162:0x0000`（报“没按”），松开瞬间读出 `vk=162:0x8000`（报“按着”）——**事件与读数整整错开一拍**。

这使「核实是否真的还按着」这个判据对**刚建立的族**必然失效：`TrackModifier` 刚写入的族，会在紧随其后的对账里被 `GetAsyncKeyState` 判为“没按”而**当场移除**。实测后果：`记账后集合` 恒为 `[]`，**所有组合开关键 100% 失灵**（任务开关与紧急停止同因，因为二者共用本机制）。

故对账**必须跳过“刚由近期事件建立”的族**：每族记录**最后一次记账时刻**（`Environment.TickCount64`，单调递增、`long` 读写原子，无需取锁），对账时若该族记账后**不足宽限期**（取 250ms），则**不参与本次残留判定**。宽限期内为假的族**一律保留**——它更可能是“按键刚发生、读数迟到”，而非“残留在案”。

**宽限期取值依据（2026-10-11 实测，宽限期版宿主跑通后回填）**：一次常规使用实测到 **53 次**对账判定落到宽限期内（跳过），全部发生在**距记账 0ms** 的事件上——即 `TrackModifier` 刚写入族、同一次回调内的对账立刻读它，读数尚未跟上；这正是修复前被当场误删、导致组合键 100% 失灵的那些事件。同一次实测中另有 **2 次**残留移除生效，距记账 **453ms / 344ms**——两者都远离记账时刻，证明宽限期并未废掉清理能力：真残留（`GetAsyncKeyState` 持续为假、无从刷新时间戳）会稳定越过 250ms 而被移除。

宽限期的正确性论证：残留的特征是**持续**为假（跨越多个事件、持续远超一瞬），而误判是**瞬间**为假。以 250ms 划界，远大于实测的“错开一拍”（毫秒级），远小于用户能感知的卡顿；UAC 漏收 key-up 后用户切回普通桌面早已超过 250ms，残留清理能力不受影响。

- **只对账已记账的族**，不做四族全量轮询：未记账 = 无残留可言，空集合时直接短路返回。于是“从不使用组合键”的配置支付零开销。
- **热路径纪律**：不分配（`List` 仅在真发现残留时才构造；命中已存在族名时字典只改计数）、不取锁、不做 IO。回调仍然永不阻塞（与上一节同一理由，§3.2 的 `LowLevelHooksTimeout` 约束）。
- **`GetAsyncKeyState` 只看高位 `0x8000`**：低位是“自上次调用后曾被按过”的历史位，与“此刻是否按下”无关，拿它做判定会得到恒真的错误结论。
- **对账是兜底，不是主路径**：正常的按下/松开仍由 `TrackModifier` 精确维护（含左右归一与计数），对账只负责收拾漏收的残局。顺序必须是「维护 → 对账 → 查表」，反过来会把本次事件刚建立的正确状态误删。

**已知限制（诚实边界）**：`GetAsyncKeyState` 在 **UAC 安全桌面持续期间**本身就可能不准（被提升的进程读到的键盘状态未必反映真实按键）。因此本机制能修的是“**回到普通桌面后残留**”这一类——而这也正是实践中最多见的场景；安全桌面**持续期间**的组合键失灵仍然无解，本设计**不声称**覆盖它。

**为什么不做“定时全量重同步”**：那需要一个后台定时器周期性轮询四个族，即使配置根本不用组合键也要永久付出唤醒 + P/Invoke 的代价，且把“永不阻塞”的回调纪律扩散到了定时器线程。对账搭在既有键盘事件上，代价只在该事件本来就要走的那条路径上增加常数级开销，且配置不用组合键时为零。

### 3.5 紧急停止键（FR-RUN-01~03、FR-RUN-07）

紧急停止是**保险丝**：用户预置一个键盘快捷键，按下即**停掉全部运行中的任务**，用于任务失控时的即时止损。它是全应用**唯一**的一个快捷键（`AppSettings.EmergencyStopKey`），不是逐任务配置。

本节只写**紧急停止特有**的机制。它与任务开关键**共用** §3.4.1 的快照与回调通道，共用部分（不可变快照、指针整体替换、族归一口径、组合命中判定、无重同步路径）一律以 §3.4.1 为准，本节不复述。

#### 3.5.1 承载：两张表同源构建

快照内**同时**承载两张表：开关键表（§3.4.1，带任务 Id）与紧急停止条目（单条目，不带任务 Id）。二者由**同一个** `ToggleSnapshot.Build(tasks, emergencyStopKey)` **一次**产出。

**为什么必须同源构建**：两张表共用同一套族归一口径（`Normalize` + `ModifierFamilies`）。分头构建则同一物理键在两个入口下的归一结果可能不一致——“配右 Ctrl、按左 Ctrl”在一张表命中、在另一张表落空，而用户看不出任何区别。此外同源构建是下面 §3.5.4“构建期排除同主键开关键”得以成立的**前提**：只有同一个构建入口，才有一个能同时看到两张表、从而执行交叉约束的地方。

**紧急停止条目独立成类型而非复用开关键条目**：后者字段含 `TaskId`，复用只能填 `Guid.Empty`，而 `Guid.Empty` 是**合法的任务 Id 值域**（`ToggleSnapshot.FromEntries` 也用它）。两个语义撞同一个值时，日后任何一次“看到 Empty 就当紧急停止 / 就当手工条目”的推断都会错。故紧急停止条目（`EmergencyStopEntry`）只带 `{ 归一主键, 修饰键族集合 }`。

#### 3.5.2 事件承载：复用 `ToggleRequested`，用载荷区分

紧急停止**不新增事件、不新增队列**，复用任务开关键的 `ToggleRequested`，靠载荷里的 `Guid?` **任务 Id 区分**：

| 载荷 `TaskId` | 含义 | 触发时机 | 是否吞键 |
|---|---|---|---|
| `null` | **紧急停止** | **按下**（down）即成立 | **不吞**（§3.5.5） |
| 非 `null` | 任务开关 | **松开**（up）时成立（§3.4 点火语义） | 按任务配置（§3.4） |

**为什么复用而非新增事件**：两条通道各自维护开关状态，迟早彼此不一致；复用一条通道则“两类命中的排队与投递顺序”天然一致，代价只是上层多读一次载荷。

**归属判定在钩子回调侧一次算定**：修饰键按下状态只在回调线程维护（§3.4.1），到了投递线程再算会用已变的状态查错任务。故任务 Id 在回调内算定、随事件带下来，门面（`HostFacade`）**不再重算**，只用它查任务（§5.4 方案 A / §6.5.2 ①）。

**上层靠“载荷是否为空”分流，不得用“按 Id 查不到任务”旁路判据**：钩子内部另有一个 `ResolveToggleTaskId` 也会返回 `null`，但那表示“这条事件确实不是任务开关”，与“载荷 `null` = 紧急停止”**语义不同、不可混用**。若上层改用“查不到任务”来判定紧急停止，则任务刚被删除、或快照与列表存在合法时间差时，一次普通开关会被误判成紧急停止而停掉全部任务。

#### 3.5.3 时间口径：紧急停止只认按下

任务开关与紧急停止的**时间口径相反**，且各有其道理，不可倒转：

- **任务开关只认松开**——点按语义在松开瞬间成立；按下的那一次事件忽略，否则一次点按会触发两轮启停。
- **紧急停止只认按下**——保险丝必须在按下的瞬间动作，松开才响不仅慢半拍，还会与“按住不放”这种最自然的应激反应相悖。松开**不重复触发**。

**因此两者不可共用同一道早退门**：门面 `ToggleRequestedHandler` 里的 `isKeyDown` 早退会把“按下事件”全部丢弃，而紧急停止恰恰依赖按下事件。故**归属判定必须排在该早退之前**——先判“是不是紧急停止”，是则只处理 down 并返回；否则再走“只认 up”的开关路径。

**时间口径的分工在门面，不在钩子侧归属解析**：钩子侧的归属解析（算“这个键属于哪个任务”）**不得**按 `isKeyDown` 过滤——它对按下与松开必须给出**同一个**任务 Id，由门面按上一条各自取舍（down 丢弃、up 生效）。

理由：`TaskId` 这一个字段同时承担两个语义——`null` = 紧急停止，非 `null` = 任务开关（§3.5.2）。若归属解析在松开那一侧返回 `null`，那条事件就不再是“任务开关的 up”，而被整个门面当成**紧急停止的 up**：门面按 §3.5.3 只认按下，于是在 `taskId is null` 分支里把这唯一能点火的事件一并丢掉——开关按下与松开两条都被丢弃，**开关键彻底失灵且无任何报错**（一条都不到达 `Scheduler.Toggle`）。这个错误在编译期与单测里都不显形（事件照常入队、门面照常返回），只表现为“开关键按了没反应”。

同理，反向也**不可**用“按下返回 `null`”来表“按下不点火”：门面的紧急停止判定是 `taskId is null && isKeyDown`，一次普通开关键按下若带 `null`，就会**被当成紧急停止而停掉全部任务**。故两条事件都必须带同一个非 `null` 的任务 Id，时间口径只由门面的 `isKeyDown` 分支承担。

#### 3.5.4 与任务开关键同键：构建期排除 + 按下优先

同键冲突分两层，口径不同、且都必要：

| 层 | 口径 | 位置 |
|---|---|---|
| **保存期** | 按**完整绑定**拒绝冲突（FR-RUN-03） | `TaskValidator` |
| **构建期** | 按**主键**排除——与紧急停止键同主键的开关绑定**不进开关键表** | `ToggleSnapshot.Build` |

**构建期为何比保存期判等更宽（只比主键，不比完整绑定）**：两张表的**查表键就是主键**，主键相同即必然同时命中；而修饰集不同时“哪一张表命中”取决于用户实际按了几个修饰键——那是不可接受的“看心情”。故主键一经相同，开关键那条一律排除。

**为何还需要构建期这一层（保存期不够吗）**：保存期校验管得住 UI 路径，**管不住手改配置文件**。构建期排除是**纵深防御**：非法配置退化为“开关键那一侧不生效”，而**紧急停止仍可用**——兜底手段在数据损坏时依然兜底。

**两层都拦不住时的兜底（回调内紧急停止优先）**：即便如此仍可能出现两者同时命中的时刻（防御网合并等），此时**紧急停止优先**——保险丝不可被开关抢走。

> **容忍键盘自动重复（auto-repeat）**：按住不放时系统会持续送 down 事件，故"按下"分支会被反复触发。
> 这条路径**不必**去重——紧急停止的动作体是逐任务 `Scheduler.Stop`，**调度器内幂等**（§3.5.7），
> 重复触发只是重复确认"已停"，无副作用。刻意不加去重标志还避免了一个反向风险：
> 去重标志一旦因某次事件丢失而卡在"已处理"，保险丝就会**失灵**——那是比重复停止严重得多的后果。
> 保险丝宁可重复劳动，不可拉闸不动。

#### 3.5.5 紧急停止不吞键（写死不可配）

任务开关键可配“吞 / 放行”（§3.4），紧急停止**一律放行**原始输入，**不提供配置项**。

**理由**：保险丝在任何情况下都首先要能**不费力地按下去**。若它会吞键，则用户按下紧急停止时若恰好在某个窗口里有输入语义，该输入被吞而紧急停止本身还未必可见——一个止损工具不该改变用户正在做的输入。这与任务开关不同：后者可能注定要吞（否则被 Ctrl 类快捷键抢键），那是任务自身的语义需要。

> **副作用（须知悉）**：紧急停止键会**照常发给系统**。因此它若与某个软件的快捷键撞车，按下时会“既停了任务、也触发了对方”。这是**不吞**这一契约的直接后果，不是缺陷；选键时避开高频快捷键即可。

#### 3.5.6 无订阅者不得静默

投递线程发现 `ToggleRequested` **无订阅者**时，事件到此为止，但**必须**留下调试输出，不得裸返回。

**理由**：“保险丝按下去没反应”与“保险丝没装”在外部表现完全相同（都是无任何反馈）。裸返回会让排查时无法区分是①没订阅、②订阅了但没命中、③命中了但被吞了。一行调试输出零成本——正常路径（已订阅）不付这个钱，异常路径至少留下痕迹。

#### 3.5.7 门面侧动作：逐任务停 + 立即可用

- **逐任务 `Scheduler.Stop`，不用 `Scheduler.StopAll`**：两者都停任务，但 `StopAll` 带“整体清场”语义（退出路径在用），而紧急停止是**用户的一次操作**，语义边界应与“再点一次开关”同类——即“停任务、不改启用状态、不碰别的”。用窄接口把语义边界守在调用点，将来 `StopAll` 若因退出路径需要加收尾动作，也不会被紧急停止莫名继承。
- **不改启用状态**：停止是运行态，启用是配置态。紧急停止后用户再点一次开关就应能重新跑起来；若做成“停用”，紧急停止就成了隐形的配置修改，用户下次启动会发现“任务怎么都不跑了”且无从归因。
- **先拍列表快照再逐个停**：遍历 `TaskRegistry.Snapshot()` 的副本而非边遍历边问注册表，避免停止过程中列表被改动引发枚举异常；已停的任务再 `Stop` 一次是安全的（调度器内幂等）。
- **改键后立即生效**：`SaveSettings` 保存成功后**先换内存设置、再重建快照**（顺序不可反——重建会去读 `CurrentSettings.EmergencyStopKey`）。不这样做则紧急停止键“改了要重启才生效”，而改键往往正是因为它与别的软件撞了，用户当场就要验证。**只在保存成功时重推**：失败时新设置没落盘，推一份基于未落盘设置的快照会造成“本次会话生效、下次启动又不是这样”的静默不一致。

## 4. 执行模型设计

### 4.1 并行调度模型

需求要求（FR-SEQ-01~05、FR-TAP-04、NFR-03）：任务内命令**并行**、各自**独立频率**、互不影响。

**模型**：**每条命令一个独立的重复节拍器（metronome）**，互不共享计时器。

```
Task (运行中)
 ├── CommandLoop #1  (键盘A·按住)      → 一次性：HoldKey(A)，然后等待任务停止
 ├── CommandLoop #2  (鼠标左键·点按 10次/秒) → 每 100ms：TapMouseButton(Left)
 └── CommandLoop #3  (鼠标移动 2次/秒)  → 每 500ms：MoveMouseAbsolute(x, y)
```

- **点按形态**：循环体 = 执行一次动作 → 等待 `1/频率` 秒 → 重复。
- **按住形态**：循环体 = 执行一次"仅按下" → 不再重复（保持按住），等待任务停止信号。
- **瞬时操作**（FR-TAP-07：鼠标移动、滚轮）：循环体 = 执行一次动作 → 等待 `1/自身频率` 秒 → 重复。

**不使用单一全局调度器**的理由：单调度器上多条命令的排队会引入相互干扰（违反 NFR-03）；独立节拍器天然满足"互不影响"，代价是线程/定时器数量随命令数增长——由 §4.2 的调度策略控制。

### 4.2 定时精度策略（对 NFR-02 的实现）

> **误差带口径的权威定义在需求文档 NFR-02**（1~50 次/秒适用 ±20ms；50 次/秒以上仅要求“实际平均频率 ≥ 配置值 90%”）。下表仅为**便于阅读的摘录**，供本节说明实现手段时参照——区间与判据的定义若有分歧，以需求文档 NFR-02 为准；NFR-02 修订时本节须同步。

频率上限 1000 次/秒 = **1ms 间隔**，这是 Windows 上极难保证精度的区间（系统计时器默认分辨率约 15.6ms）。**这必须提前挑明**：

| 频率区间 | 间隔 | 可达性判断 |
|---|---|---|
| 1~10 次/秒 | 100~1000ms | 轻松达成 ±20ms |
| 10~50 次/秒 | 20~100ms | 可达成，但需提高系统计时器分辨率 |
| 50~1000 次/秒 | 1~20ms | **±20ms 误差带不适用**（带宽大于间隔本身）。需求口径已明确：此区间以"实际平均频率 ≥ 配置值 90%"为验收指标（需求文档 NFR-02） |

**关键矛盾（已裁定）**：NFR-02 的 ±20ms 误差带在 1000 次/秒（1ms）时相对误差达 2000%——该指标在数学上无意义（间隔本身就小于误差带）。**裁定结论**：NFR-02 明确为 **1~50 次/秒适用 ±20ms**；50 次/秒以上改用"实际平均频率 ≥ 配置值 90%"作为验收指标（需求文档 NFR-02 已更新，裁定存档见 §9.1 Q-D1）。

**设计上的应对**：
1. **提高计时器分辨率**：通过 `timeBeginPeriod`（winmm）将系统计时器分辨率提升至 1ms，退出时用 `timeEndPeriod` 还原。**已实测支撑（§9.3 V-2）**：不开时均偏差 5.6~6.2ms（被 15.6ms 时钟粒度拉长），开启后降至微秒级，差异达三个数量级。
2. **重复节拍器用"绝对时间轴"而非"相对睡眠累积"**：以启动时刻为基准，第 n 次动作的目标时刻 = `t0 + n × (1/频率)`，每次计算下一次目标时刻并睡眠到该时刻。**避免累积漂移**（这是精度控制的核心手法：睡眠误差不逐次叠加）。
3. **每个命令一个轻量循环**：优先用**专用线程 + 高精度等待**，而非 `Task.Delay`（后者精度受线程池调度影响）。线程数上限由命令总数决定（见 §4.3）。**实测澄清（§9.3 V-2）**：在 `timeBeginPeriod(1)` 生效前提下，10~200 次/秒区间专用线程与线程池的**精度无可区分**；保留专用线程的理由是**可控性**（线程数不受全局并发影响、可设 `Highest` 优先级、长驻任务不占池线程），非精度。
4. `timeBeginPeriod` 的代价（影响系统能耗，Win10 1809 上生效）——仅在**有任务运行时**调用，全部停止后还原。

### 4.3 并发规模控制

FR-TASK-09 与 Q4 定案："同时运行的任务数量不设上限"，Q2："任务内命令数不设上限"。二者相乘意味着**线程数可能极大**。

**设计口径**：
- 每条命令对应一个逻辑节拍器（§4.1 的模型不变，这是需求语义，不可变）；
- 但**物理承载**（1 命令 = 1 线程 vs 1 命令 = 1 定时器回调）是实现细节，可按实测调整；
- 设计上采用**"逻辑独立、物理复用"**：为高频命令（如 ≥50 次/秒）分配专用线程；低频命令（如 <50 次/秒，间隔 ≥20ms）共享一个调度池——因为它们的抖动容忍度足以被池化。**该阈值划分实测对精度不敏感**（§9.3 V-2：在 `timeBeginPeriod(1)` 生效前提下，10~200 次/秒区间专用线程与调度池精度无可区分），故保留为**工程取舍**（隔离性 / 线程数可控），不因精度理由而改。

> 这里显式标注一个**架构取舍**：物理复用会引入理论上的相互影响，与 NFR-03"互不影响"存在张力。实测表明池化与专用线程在 10~200 次/秒区间精度不可区分（§9.3 V-2），且 20 条并行下达成率 ≥99.3% → **池化在精度维度上安全**；隔离性维度仍按上述阈值划分保障。**验收判据是可测的**（AC-23 / AC-23a / AC-23b），不属于猜测。
>
> **降级口径**：池化被定义为**可选优化**而非精度必需——若实现期证明"1 命令 1 线程"在最大并发下已满足 NFR-02 / AC-23 系列，则不实施池化（回头也符合设计）。池化仅作为"命令数很多且需控制线程数"时的工程手段。

### 4.4 停止与"补发松开"（FR-SEQ-06/07、FR-RUN-05）

**停止流程**（必须做到"立即停止，不得在停止后继续发出"）：
1. 置该任务的**停止标志**（原子变量）；
2. 唤醒所有处于等待中的命令循环，令其**检查标志后立即退出**，不再发出任何事件；
3. 遍历 `InputSimulator` 的"当前按住集合"，补发**松开事件**；
4. 清空该任务的按住集合条目，状态置为"已停止"，通知 UI。

**时序细节**（避免"停止瞬间刚好发出一次动作"）：
- 循环体在**执行动作前**先检查停止标志，执行后再检查一次再进入等待；
- 停止流程先置标志，**再**补发松开——因此不会出现"补发松开之后，某个正在执行的循环又按下"的竞态。

**补发松开的顺序**（FR-TAP-06 明确要求）：
- 组合键按住形态：**主键先松、修饰键后松**（否则修饰键先松会导致主键被当作单键发出）；
- 普通按住：直接松开；
- 多条按住命令的松开顺序**无要求**（不同键之间无依赖），但需保证**同一条组合键内部**的顺序。

### 4.5 启停的并发契约（AC-03、AC-15/AC-16、FR-RUN-04）

§4.4 规定的是**单次停止内部的步骤顺序**；本节规定的是**多次启停请求并发交叠时**的裁决规则——
用户快速连点开关（AC-03 的测法）会让 `Toggle` 的多个实例同时在途，调度器必须给出确定的结果。

**占位与启动不可分割**（AC-03）：
调度器以「运行表是否含该任务 Id」为唯一运行态判据。若"判定未运行"与"写入运行表"分处两次取锁，
两次并发点按可能都判出未运行而双双启动，同一任务便出现两个运行期、互相叠加注入。
因此启动路径固定为**两步**：

1. **锁内占位**——锁内二次检查 Id 不在表中，随即写入占位运行期；
2. **锁外启动**——锁外调用运行期的启动，真正拉起命令循环。

即"占位"先于"起线程"，去重完全由第 1 步锁内那一次检查承担。

**为何不把两步并成一把锁**：停止的实质工作（补发松开）会取 `InputSimulator` 的锁（§3.1.3），
若在持调度器锁时调用即形成锁序耦合（调度锁 → 注入锁）。故启停两条路径统一收敛为
**"锁内只做状态迁移、锁外做实质工作"**，占位窗口因此客观存在——它是锁序安全的代价，由下列两条规则兜住。

**占位窗口内的竞态收敛**：
- **停止先到**：停止可能落在"已占位、循环未拉起"的窗口内。此时运行期**不静默返回**，
  而是留下"启动前已被要求停止"的印记，由随后的启动消费并放弃拉起循环——
  否则该运行期已不在运行表内却仍在注入，无人能停。
- **启动后易主**：锁外启动期间，并发点按可能已把运行表换成另一个运行期
  （停掉本运行期、或另起了新占位）。启动结束时必须**重新确认所有权**：
  仅当运行表仍指向本运行期才算启动成功；否则本运行期自行停下。
  身份确认与"宣告运行成功"必须落在**同一次取锁**内完成——
  若分两次取锁，中间可能插进一次"停止全部"（它清表并停掉本运行期），
  而本方法随后仍对外宣告"已启动"，UI 便会显示一个并不在跑的任务（AC-15/AC-16）。
- **撤占位须认身份**：上述任一路径撤除占位时，都必须**先确认运行表仍指向自己**再删。
  若不加判定地按 Id 删除，删掉的可能是并发点按刚建立的**新**占位——
  新运行期随即被拉起却不在运行表里，从此无人能停（表现为"停止全部"后仍持续注入）。

**"停止全部"的原子清表**（FR-RUN-04、AC-15/AC-16）：
先**一次性清空**运行表、再在锁外逐个停止。清空后新到的启动请求不会被"正在停"的状态干扰；
逐个停止各自 try，单个失败不中断整体紧急停止（NFR-08"随时可终止"）。

**紧急停止的触发链路（FR-RUN-01/FR-RUN-07）**：

紧急停止与任务开关**共用同一条钩子链路**（同一个 `WH_KEYBOARD_LL` 回调、同一套"按下集合"判定），
不新增第二条监听路径、不新增事件类型：

1. **钩子回调（Input 层）**——两种触发源的归属判定都排在 `isKeyDown` 早退**之前**：
   - 任务开关只认**松开**（up）；紧急停止只认**按下**（down）；
   - 两者都按"当前按下集合 + 修饰键族"匹配**完整绑定**，各自维护自己的"已命中待松"状态；
2. **投递（Input → Engine）**——命中紧急停止时，钩子以**已有的** `ToggleRequested` 事件上报，
   载荷为 `Guid?`：**`null` = 紧急停止**，非空 = 任务 Id。上层**靠该载荷是否为空**分流，
   **不得**用"按任务 Id 查不到任务"之类的旁路判据——那会把"任务已被删除"误当紧急停止；
3. **执行（Engine）**——`HostFacade` 收到载荷为 `null` 即执行紧急停止：
   **逐任务 `Scheduler.Stop`**（§3.5.7）——不用 `StopAll`，后者带"整体清场"语义、属退出路径；
4. **吞放行（回调返回值）**——**紧急停止不吞键**：命中紧急停止的按键照常 `CallNextHookEx` 传给前台程序。
   紧急停止的语义是"停止本工具的注入"，而非"夺走这个键"（AC-32a）。

**同键时的裁决（FR-RUN-07）**：紧急停止快捷键与某任务的开关按键冲突时，**以紧急停止为准**——
构建期排除与该紧急停止键**同主键**的开关绑定（§3.5.4），该任务的开关键在此配置下不生效，
紧急停止照常可用。这不是"附加效果"，而是一次**明确的优先级裁决**：保险丝不得被开关抢走。

**该配置正常不可达**：保存期按**完整绑定**判等（§5.3）即已拒绝"紧急停止键 = 某任务开关键"，
故上述状态只能由**手工改坏配置文件**产生。构建期排除是**纵深防御**——
保存期那道门是给正常使用守的，构建期这道是给"绕过保存期"守的；
两层都漏时（例如族归一后主键撞上但修饰集不同），回调内仍由紧急停止优先兜底。

| 事件 | 动作 | 是否吞键 |
|---|---|---|
| 该键**按下** | 触发紧急停止（停止全部任务） | **否**——照常传递（AC-32a） |
| 该键**松开** | 无动作（开关绑定已被构建期排除） | 否 |

**设计取舍（为何不新增 `EmergencyStopRequested` 事件）**：新增一个只承载"停全部"这一种语义的事件，
会让 `HostFacade` 多接一条订阅、多一条测试面，而两条路径的**执行体完全相同**（都是 `StopAll()`）。
`Guid?` 的空值即天然表达了"没有具体任务"这一语义，比另一个事件类型更少面。

## 5. 任务模型

### 5.1 领域对象

```
Task
 ├─ Id            (GUID，内部标识)
 ├─ Name          (string，列表内唯一 → FR-TASK-06)

Command (抽象)
 ├─ TapMode       (None | Tap | Hold，仅键盘/鼠标按键命令适用 → FR-TAP-01)

 ├─ KeyboardKeyCommand  { VirtualKey }                       (FR-CMD-K1)

 ├─ MouseButtonCommand  { Button }                           (FR-CMD-M2)
```

### 5.2 开关按键的表示

`KeyBinding` 需统一表示**键盘键**与**鼠标键**（FR-TOGGLE-01）：

| 来源 | 标识 |
|---|---|
| 键盘 | `VirtualKey`（虚拟键码，如 F6 / Ctrl） |
| 鼠标 | 按键枚举（左/右/中/X1/X2） |

**按键捕获**（FR-TOGGLE-02）通过钩子实现："录制按键"期间，钩子把下一个非 injected 的按键事件上报给 UI 并**消费**掉（避免录制时误触发），界面显示捕获到的键名。**不允许手输**——UI 上只提供捕获按钮，不提供文本框。

**捕获会话的两个集合（分工不可合并）**：一次捕获会话内钩子维护两个集合，二者**语义不同、不得用同一个集合承担**：

| 集合 | 语义 | 增 / 减 | 服务的判据 |
|---|---|---|---|
| 按下集 | **此刻还按着**的键 | 按下入集；**松开移出** | 完成判据：集合清空 = 所有已按下的键都松开了 |
| 并集 | **本次会话按过的**键 | 按下入集（去重）；松开**不移除** | 结果快照：交出并集 |

**为什么必须分开**：完成判据要求"松开至集合为空"，而完成的那一刻按下集**恰好被抽干**。若用按下集当结果来源，快照必然取到空数组，捕获结果是**恒为空集**——表现为"点捕获不捕获任何按键"（2026-10-09 实测：按下 `LeftCtrl`/`D2` 均被记录，结果却是 0 键）。两个集合的分工是这条链路的正确性要件，不是实现细节。

**录制口径（吞 / 放行）**：按下时**吞掉**（不投递给系统和上层，避免录制期间误触发别的程序），松开时**放行**。

**会话归零**：两个集合都在三个复位点清零——开始录制、取消录制、取出结果（无论取出的是结果还是空）。上一次录的键不得混进下一次会话的结果。

**由按键集合折出绑定（方案 A，2026-10-09 裁定）**：一次捕获会话交出的是**整个会话按过的键**（上一表"并集"，顺序 = 按下顺序）。绑定由该集合**折出**，不得直接照搬集合，口径如下：

| 集合形态 | 主键 | 修饰集 | 绑定形态 |
|---|---|---|---|
| **单个**非修饰键 | 该键 | **空** | 单键：`KeyBinding.FromKey` |
| 含**非修饰键**（≥2 键） | **第一个非修饰键** | **全部**修饰键（每族代表键），**含主键所在族** | 组合：`KeyBinding.FromCombo` |
| 仅**修饰键**（≥1 个） | 固定族序 `Ctrl→Alt→Shift→Win` 中**首个命中**的族代表键 | 同上（含主键所在族） | 组合：`KeyBinding.FromCombo` |
| 鼠标键（不参与组合，§3.4） | 该鼠标键 | 空 | 单键：`KeyBinding.FromKey` |

三条不可动摇的口径：

1. **主键只可能是非修饰键。** 修饰键在绑定里以**修饰身份**参与（"必须按着哪个键"）；把非修饰键塞进修饰集，会被下游的族归一（§3.4.1 / §5.3 的主键判等）整个丢掉，`Ctrl+F8` 静默退化成裸 `Ctrl`。
2. **主键所在族也在修饰集内。** 全为修饰键时（用户就录了 `Ctrl+Shift`），该键同时是"按的是哪个键"与"必须按着哪个修饰键"——同一件事的两个说法。少写一半，`Ctrl+Shift` 退化成 `Ctrl`。
3. **主键必须取族代表键**（`KeyCatalog.RepresentativeOfFamily`，族定义见 §3.1 的键归一口径）。下游一律按族归一判等（左右 Ctrl 同族）；若拿用户实按的那把（可能是右 Ctrl）当主键，查表**查不中**，表现为"钩子命中了、引擎却找不到任务"（§5.4 已论证的失配路径）。

**单键与组合是两种绑定形态**（§3.4.1 命中判定即按此分派：单键 / 鼠标键**不做**修饰键判定，组合才判修饰集包含）：无修饰 → `FromKey`，有修饰 → `FromCombo`。**不得**写成"修饰集为空的组合"——那会让单键落进组合分支。

> 由上表可推得一条恒等关系：**集合长度 < 2（且非鼠标）⇒ 必为单键形态；集合长度 ≥ 2 ⇒ 必含修饰键 ⇒ 必为组合形态。** 因为非修饰键至多有一个能进主键，其余键只可能是修饰键。

**裸键误触提示**：单键形态的开关键（未配任何修饰键）意味着**主键即全部条件**——用户按 `Ctrl+F6` 与按裸 `F6` 都会命中该任务的开关（§3.4.1 的判定口径）。这是一个容易误触的形态，且 F 系列功能键常与其他程序的热键重合。故编辑页在用户录制出一个**单键**开关键时给出非阻断提示，引导其改配组合键；提示不阻止保存（单键是合法配置，FR-TOGGLE-01 未禁止）。

### 5.3 保存时校验（对应多条 FR 的"拒绝保存"）

保存是**集中校验点**，全部通过才落盘。校验清单：

| 校验 | 违反时 | 需求 |
|---|---|---|
| 任务名非空且在列表内唯一 | 拒绝 + 提示改名 | FR-TASK-06 |
| 命令集合非空 | 拒绝 | FR-SEQ-08 |
| 点按频率在 1~1000 内 | 拒绝 + 提示 | FR-TAP-05 |
| 开关按键未被其他任务占用（**按主键判等**） | 拒绝 + 提示冲突 | FR-TOGGLE-05 |
| 开关按键不与**本任务**命令集合内的实体键重叠 | 拒绝 + 提示 | FR-TOGGLE-07 |
| 同一实体键不同时存在"按住"与"点按"两条命令 | 拒绝 + 提示 | FR-SEQ-10 |
| 紧急停止快捷键不与任何任务开关按键冲突（**按完整绑定判等**） | 拒绝 + 提示 | FR-RUN-03 |

> 上表两行判等口径**不同**，不可合并：`FR-TOGGLE-05` 只比主键（一个主键不得服务两个任务），
> `FR-RUN-03` 比完整绑定（修饰集 + 主键都相同才会在同一次点按上真正重叠）。
> 对应实现 `TaskValidator.IsSameToggleKey` 与 `TaskValidator.IsSameBinding`，两者语义各自独立。

> **"紧急停止 vs 开关按键冲突"的裁决是"紧急停止优先"**：`FR-RUN-03` 拦的是"用户把紧急停止快捷键
> 配成某个**任务**的开关键"这类**显式冲突**——保存期即拒绝（FR-RUN-03，本处只比完整绑定）。
> 若该状态仍被手工改配置绕过，则构建期排除该开关绑定（§3.5.4），**紧急停止照常可用、开关键不生效**
> ——保险丝不得被开关抢走（FR-RUN-07、§3.5.4、§4.5、AC-32a）。

> 校验规则集中在**一个**校验器模块中，UI 保存时调用；避免规则散落在 UI 各处。

**复制任务（FR-TASK-04）的语义**：复制 = 对任务做**深拷贝**（命令集合逐条新建，不共享引用），生成的新任务名自动加后缀（如"任务名 - 副本"）；副本**必须重新过一遍上述全校验**——特别是任务名唯一性与开关按键占用（副本默认沿用源任务的开关按键，而该键已被源任务占用 → 必须提示用户重新指定）。

### 5.4 开关命中所需的任务信息（S9 裁定：方案 A）

§3.4.1 的快照把「物理键 → 该键要吞还是放行」压成了一次查表，但**查表只能给出布尔位，给不出"这是哪个任务"**。Engine 层收到 `ToggleRequested` 后要调 `Scheduler.Toggle(task)`，就必须知道命中的是哪一个任务。

**裁定：把任务 Id 并入快照条目本身**（用户 2026-10-09 裁定，方案 A）。

| 项 | 口径 |
|---|---|
| 快照条目 | 由 `{ 修饰键族集合, consume, IsCombo }` 扩为**再带一个 `Guid`（所属任务 Id）** |
| 新增读取面 | **只加一个**方法：由物理键取该任务 Id；既有 `TryGetConsume` 的签名与语义**一个字不改** |
| 谁负责族归一 | **快照内部负责**。调用方（Engine）传**原始物理键**即可——"配右 Ctrl、按左 Ctrl"由快照的归一步骤抹平，Engine 不重复一遍归一规则 |
| 来源 | 任务 Id 由 `ToggleSnapshot.Build` 从任务定义注入——构建快照时本就在遍历任务，零额外遍历 |

**为什么不选"Engine 自建一张查找表"**（备选 B）：单查 `TryGetConsume` 得到的只是**归一后的主键**，而任务的 `ToggleKey.Trigger` 保存的是**原始键**——配右 Ctrl 的任务，用归一键去查任务表会**查不中**。若要让 B 成立，Engine 必须另建一张**与快照同口径的**归一索引，即把同一套归一规则维护成两份——两份规则一旦不同步，就会出现"钩子命中了、Engine 却找不到任务"的静默失配。方案 A 让唯一的归一实现服务两个用途（吞放行判定 + 任务定位），不存在这条失配路径。

**冲突口径（用户 2026-10-09 裁定：不可达）**：同主键的**任务级**冲突在**保存期即被拒绝**（§5.3 FR-TOGGLE-05 主键判等，§3.4.1 已论证"同主键一律拒绝"），故"一个主键对应多个任务"在**生产路径不可达**。§3.4.1 的确定性合并（`ToggleEntry.Merge`）因此**保留为防御网**（手改坏配置的自愈），**不承载产品语义**：它不定义"同键时哪个任务胜出"，因为合法数据里不存在这个情形。

## 6. 界面层设计

### 6.1 页面结构

| 界面 | 内容 | 对应需求 |
|---|---|---|
| **任务列表页** | 任务卡片/列表：名称、开关按键、状态标识（运行中/已停止）、启用开关；操作：新建/编辑/复制/删除；**“停止全部任务”按钮**（一键停止所有运行中任务） | FR-TASK-01~04、FR-TOGGLE-04、FR-RUN-04 |
| **任务编辑页** | 任务名、开关按键（捕获）、命令列表（增删改，无排序）；每条命令：类型（下拉）、参数、执行形态（点按/按住/不适用）、频率 | FR-SEQ-01/09、FR-UI-04 |
| **设置页** | 紧急停止快捷键（含**可用性提示**：若该组合已被系统或其他软件占用，提示“该键可能不可用”并引导更换） | FR-RUN-01/02/06 |
| **托盘菜单** | 显示主窗口 / 停止全部任务 / 退出 | FR-UI-02 |

**紧急停止快捷键的占用检测（FR-RUN-06 / AC-27）**：设置页提供快捷键配置，用户设定该组合时做**可用性探测**——尝试以 `RegisterHotKey` 试注册该组合，失败（已被其他进程占用）则提示"该键可能不可用"并引导更换；成功则立即注销。即使试注册成功，也在提示中说明该键可能与系统快捷键语义重叠。

> 注：本工具的紧急停止**用低级钩子监听**（§3.2），而非 `RegisterHotKey`——后者会**独占**该组合并使其不再传递给前台程序，与"全局监听且不干扰其他软件"的目标相悖。`RegisterHotKey` 在此**仅作为探测手段**（试注册后立即注销），不用作实际监听。其占用语义需实现期实测确认（§9.2 V-6）。

### 6.2 交互约定（对应需求明文约束）

- **状态实时显示**（FR-TOGGLE-04）：运行状态由 Engine 通过事件通知 UI，UI 更新状态标识并播放过渡动画（NFR-11）。
- **固定取值用选择控件**（FR-UI-04）：命令类型、鼠标按键、滚轮方向、执行形态**一律**使用下拉/单选/按钮，不得出现文本框。
- **删除二次确认**（FR-TASK-03）：删除任务前弹确认对话框。
- **弹窗必须串行**（平台约束）：同一 `XamlRoot` 上只允许一个 `ContentDialog` 在屏，并发 `ShowAsync()` 会抛 `COMException (0x80000019)`。三个业务页各持一把 `SemaphoreSlim(1,1)` 串行闸，**所有**弹窗（确认框、提示框）经统一入口 `ShowDialogAsync` 弹出；并发弹窗退化为**排队**（先确认第一个、再确认第二个），而非抛异常。
  - 锁**只包住 `ShowAsync` 一句**，业务逻辑（落库、重载列表）一律在锁外——否则用户在弹窗上停留时整页僵住。
  - 任何页面**不得**绕过统一入口直调 `ShowAsync()`；也不得在持锁期间调用会弹窗的方法（自死锁）。
  - 崩溃后果特别严重的场景是列表页：其提示方法曾是 `async void`（异常无出口），与删除确认框撞车即成为**进程级未处理异常**——宿主带 `requireAdministrator`，崩溃后用户需重新提权启动。
- **中文界面**（FR-UI-05）：全部界面文案为中文，不引入多语言框架。
- **过渡动画**（NFR-11）：任务启停、保存成功/失败、窗口显隐配过渡动画；动画**不阻塞**主线程；响应系统"减少动画"设置。

### 6.3 系统托盘（WinUI 3 的已知缺口）

WinUI 3 **无内建托盘 API**（§1.3 已述）。方案：

- 通过 P/Invoke 调用 `Shell_NotifyIcon`（`shell32.dll`）添加托盘图标，并在窗口消息循环中处理自定义回调消息；
- **消息窗口取 WinUI 3 主窗口的 HWND**（`WindowNative.GetWindowHandle`，在窗口 `Activated` 后取得）；该 HWND 的窗口过程需子类化（`SetWindowLongPtr`）以拦截自定义回调消息。**不另建专用 Win32 消息窗口**——已实测该做法可行（§9.3 V-3）；
- 托盘菜单用 Win32 `CreatePopupMenu` / `TrackPopupMenu` 弹出（`TPM_RETURNCMD | TPM_NONOTIFY`），弹出前须先 `SetForegroundWindow`，否则菜单不消失；
- 关闭主窗口时**隐藏而非退出**（FR-UI-01）；退出走托盘菜单（FR-UI-02）。

**S9 设计要点（子类化的安全边界）**：子类化 WinUI 主窗口的 WndProc 属于**侵入框架内部**的互操作，两条纪律不得违反：

| 纪律 | 理由 |
|---|---|
| **必须保存原 WndProc 并在默认分支转调它** | 主窗口承载 WinUI 3 自身的全部消息（布局、DPI、激活、输入）；吞掉任何一条都会让 UI 出现难以归因的故障。回调只**识别**自己的自定义消息，其余一律 `CallWindowProc(原过程, …)` |
| 自定义消息取值**避开**系统保留区 | `WM_APP`（`0x8000`）起是安全的自定义区间（`WM_APP + n`）；托盘回调消息与「第二实例唤起」消息各占一个 |

**菜单三项**（FR-UI-02，§6.1 已列）：

| 项 | 行为 | 对应 |
|---|---|---|
| 显示主窗口 | `ShowWindow` + `SetForegroundWindow` 唤起并激活主窗口 | FR-UI-01 |
| 停止全部任务 | 调 `Scheduler.StopAll()`（§4.5 原子清表），**不退出进程** | FR-RUN-04 |
| 退出 | 停止全部任务 → 补发松开（§3.1.3 `ReleaseAllAll`）→ 真正退出进程 | FR-UI-02、AC-32 |

**「停止全部任务」与「退出」是两个独立入口**（§10 明文）：前者只停任务、程序继续驻留；后者在停任务之外还**结束进程**。二者都必须在返回前完成补发松开（AC-32）。

**托盘图标的启动失败路径**：`Shell_NotifyIcon(NIM_ADD)` 失败（如任务栏不可用）时不静默——记日志并告知用户，程序仍可运行（只是托盘不可达，关窗后需经任务管理器结束）。**不因托盘失败而拒绝启动**。

### 6.4 单实例（NFR-09）

使用命名互斥体（`CreateMutex` + 唯一名称）实现：第二实例启动检测到互斥体已存在时，提示"程序已在运行"并把焦点交给已有实例窗口（AC-30）。

**焦点移交的手段（S9 裁定：`FindWindow` + `PostMessage`）**：互斥体只能回答"是不是已有实例"，**回答不了"它在哪个窗口"**——两个进程之间没有任何共享的窗口句柄。故第二实例在确认互斥体已存在后，用 `FindWindow(窗口类名, 窗口标题)` 找到第一实例的主窗口，向它 `PostMessage(WM_APP + 1)`；第一实例的子类化 WndProc（§6.3）收到该消息即执行「显示主窗口」（与托盘第一项同一条路径）。

| 选型 | 结论 | 理由 |
|---|---|---|
| `FindWindow` + `PostMessage` | **采用** | 零额外依赖、零 IPC 通道、无序列化；`PostMessage` 异步入队，第二实例**发完即退**，不等对方处理 |
| 命名管道 / 共享内存 | 否 | 为一个"把窗口拉到前台"的单一动作引入通道生命周期、消息协议与并发处理，投入与收益不成比例 |

**两个必须交代的边界**：

1. **窗口类名/标题不是稳定契约**——WinUI 3 主窗口的类名由框架生成，标题即应用标题（可能随文案变化）。故**不依赖标题匹配**：注册一个**自己的窗口类名**或将首实例窗口标题固定为应用的稳定标识符，`FindWindow` 只按该稳定标识匹配。取值的具体形态在实现期定，但"必须有一个不随 UI 文案漂移的稳定标识"是本设计的硬要求。
2. **首实例可能尚未建好窗口**——第二实例启动时，第一实例或许还在初始化（互斥体已建、窗口尚未创建）。此时 `FindWindow` 返回 `NULL`。**处理口径：找不到就只提示"程序已在运行"，不重试、不轮询**（AC-30 只要求"不产生第二个实例 + 给出提示"，焦点移交是**尽力而为**的增强，不构成 AC 判据）。

### 6.5 组合根接线（`HostFacade`）

§2.2 已定装配落 `src/Host/Engine/HostFacade.cs`。本节给出**接线全图**与**五条容易接错的线**——本类是进程内唯一的装配点，接错一处就是端到端不工作，且症状往往出现在离错误很远的地方（"点开关没反应"）。

#### 6.5.1 接线全图

| 接线 | 方向 | 说明 |
|---|---|---|
| `JsonConfigStore` → `TaskRegistry` | 构造注入 | Registry 的构造参数即存储；`Load()` 载入列表并立刻回写一次归一结果（§5.2） |
| `SendInputSink` → `InputSimulator` → `Scheduler` | 构造注入 | 全进程**只有一个** `InputSimulator`（按住表是全局唯一一张，§3.1.1），故必须先建 Simulator 再建 Scheduler |
| `HookService` | 独立持有 | 进程内唯一实例；`Start()` 装钩子、`Dispose()` 摘钩子（§3.2） |
| `HookService.ToggleRequested` → 查表 → `Scheduler.Toggle` | **事件订阅** | 钩子事件由投递线程抛出（`HookService.cs:192`、投递线程 `:877`），订阅回调必须**立刻返回**、不得做耗时工作 |
| 任务列表变更 → `ToggleSnapshot.Build` → `HookService.UpdateToggleTable` | **单向推送** | 每次增删改任务后重建快照并整体替换（§3.4.1 指针替换）；漏推的后果是"新任务的开关键不生效" |
| `Scheduler.RunStateChanged` → UI | **Engine→UI 唯一推送通道** | 见 §6.5.3；UI 不得反过来轮询 `IsRunning` 去驱动显示 |

#### 6.5.2 开关命中链路的三条易错线

**① 「键 → 任务 Id」的查表由门面自持，不查 `TaskRegistry`。**

§5.4（方案 A）已裁定任务 Id 并入快照条目：门面订阅 `ToggleRequested` 后，用钩子给的**物理键**取任务 Id。这条表**必须与快照同源**——即由同一份 `ToggleSnapshot` 提供这次查询，而非在门面里另起一张"物理键 → 任务"的表。理由是 §5.4:523 已论证的失配路径：快照内部负责族归一，`TaskDefinition.ToggleKey.Trigger` 保存的是原始键，配右 Ctrl 的任务用归一键查任务表会**查不中**。让唯一的归一实现服务两个用途，不维护第二份归一规则。

**② 查不到任务即丢弃，不得猜测。**

键在表内但对应任务**已被删除或已禁用**——这是合法且常见的中间态（用户删任务的同时钩子事件正在投递队列里排队）。此时**静默丢弃**该事件，不报错、不兜底启动别的任务。

**③ 任务 Id 必须在入库前分配，`Guid.Empty` 是保留哨兵值。**

界面新建路径（`TaskDraft.CreateNew`）产出的草稿，其 `Id` 显式写作 `Guid.Empty`，表示"这是新任务、还没有身份"。**分配点唯一**：门面 `AddTask` 在**校验之前**调用 `TaskDefinition.EnsureId()` 补齐（`HostFacade.cs` / `TaskDefinition.cs`），且只在为 `Guid.Empty` 时补——按 Id 显式构造的任务（配置导入、测试夹具）不被改写。

这条必须写死而非"顺手补一行"，是因为 `Guid.Empty` 在本系统里**已被另一处语义占用**：开关快照用空 `Guid` 表示"这次点按没有命中任何任务"（`ToggleSnapshot` 的未命中哨兵）。若新建任务的 Id 恰等于该哨兵值，后果不是显示异常而是**功能失效**：

| 漏分配的后果 | 表现 |
|---|---|
| Id == 哨兵值 | 钩子侧把该任务的开关键判定为"未命中" → **新建任务的开关键完全失效**（对应 §6.5.2 ①/② 的丢弃路径） |
| 多个新建任务共用空 Id | 按 Id 定位（编辑 / 删除 / 停止 / 运行态查询）全部退化为命中"第一个"，其余任务不可单独操作 |

因此纪律是：**任何进入 `TaskRegistry` 的任务都必须带非空 Id**，由门面这一道关兜住；`TaskDefinition.EnsureId()` 是该不变式的唯一实现点（落在 Core，以便被纯逻辑单测覆盖——宿主带管理员清单，不进测试进程）。

**已知未闭环的两个入口**（代码评审 2026-10-09 记录，均无 UI 路径可达）：

| 入口 | 现状 | 为何暂不处理 |
|---|---|---|
| `HostFacade.ReplaceAllTasks`（批量替换） | 不过 `EnsureId` 闸 | 该路径的调用方（批量导入）本就按 Id 显式构造任务，与"不被改写"一脉相承；且当前无任何 UI 调用方。 |
| `JsonConfigStore.LoadTasks` → `TaskRegistry.Load` | 均不归一化空 `Id` | 触发条件仅限**手工编辑 `tasks.json`** 写入全零 Id；无 UI 路径可产出该文件，且 AC-21（不崩）仍成立，只是任务语义中毒。 |

#### 6.5.3 `RunStateChanged` 的订阅口径

`Scheduler.RunStateChanged`（`Scheduler.cs:58-69`）是 **Engine → UI 的唯一推送通道**，但它**不代表"循环已在跑"**——它只表达调度器对"表内有无此任务"的观测结论。且 `false` 的通知时机**随路径而异**：`Toggle` / `Stop` 是在该任务停完后逐条发，`StopAll` 是先把所有任务停完、再逐条补发。

| 订阅方的正确用法 | 禁止的用法 |
|---|---|
| 收到事件 → **重读运行态**（`Scheduler.IsRunning(id)` 或 `RunningTaskIds`，`Scheduler.cs:91`/`:100`）→ 更新该项显示 | 把"收到 `true`"直接当作"循环已在注入"；或据事件先后推断因果（如"先收到 A 的 false、再收到 B 的 false，所以 B 在 A 之后停"） |

UI 刷新须**封送到界面线程**（事件在调度线程上抛出，`StopAll` 路径上更是在调用方的线程上）。

#### 6.5.4 门面必须自持「修饰键按下态」

快照判定组合开关时需要一个"当前按下了哪些修饰键族"的输入，而这件事的权威状态在 `HookService._pressedModifierFamilies`（`HookService.cs:107`）——它是 **private**，且只在钩子回调线程上读写（`:786` 注释明示"无锁无分配"是为回调性能服务）。

因此门面**必须自持一份修饰键按下态的镜像**（订阅 `ToggleRequested` 的前置事件，或由钩子在同一事件里附带上报），**不能**去读钩子内部字段、更不能为此给钩子加锁——那会把锁引入钩子回调路径，与 §3.2 的"回调最小化"硬约束冲突。

#### 6.5.5 托盘与单实例的落地接口

| 项 | 接口 |
|---|---|
| 托盘消息窗口 | WinUI 主窗口 HWND（`WindowNative.GetWindowHandle`，**须在 `Activated` 之后**取） |
| 自定义消息取值 | `WM_APP + n` 各占一个：`WM_APP + 1` = 第二实例唤起（§6.4）；托盘回调消息另取一个 `WM_APP + n`（§6.3 纪律：各占一个，不得复用） |
| 托盘三项的行为 | 见 §6.3 表；「停止全部」走 `Scheduler.StopAll`（§4.5 原子清表），「退出」走 `Scheduler.Shutdown`（含补发松开兜底，`Scheduler.cs:375`） |
| 单实例互斥体 | 主窗口创建**之前**检测；已存在则提示 + `FindWindow` + `PostMessage(WM_APP + 1)` 后**发完即退**（§6.4） |

**退出路径的唯一入口是 `Scheduler.Shutdown()`**：它内含 `StopAll` + `InputSimulator.ReleaseAllAll()` 两层保障（§3.1.3 兜底）。托盘退出、窗口关闭、异常结束路径都应收敛到它，不得各自写一套停任务逻辑。

## 7. 配置持久化设计

### 7.1 存储格式与位置

- **位置**：`%APPDATA%\<软件名>\`（FR-CFG-01）；
- **格式**：JSON（人类可读、便于排查；损坏处理的容错路径清晰）；
- **文件**：任务配置与全局设置分文件存放（如 `tasks.json` / `settings.json`），避免一处损坏拖垮全部；
- **写入时机**：保存时**整体写入**（先写临时文件，再原子替换），避免写一半断电导致文件半损坏。

**写入结果契约 `ConfigSaveResult`**：以 `Ok(AppSettings? value = null)` 作为**唯一**成功构造入口
（不另设 `OkWith` 之类的第二工厂——工厂多一个，调用点就有两种写法，分歧必现）。
是否携带一份 `AppSettings` 取决于**本次写入是否真的落了设置**：`SaveSettings` 传 `document.Settings`，
`SaveTasks` 不传（`Value == null`）。上层要写回"实际落盘的那一份"时**先判空**——
`Value == null` 表示"这次写的是任务，没有设置可写回"，**不得**据此推断"设置落盘失败"。
失败路径统一走 `ConfigSaveResult.Error(...)`，与上述成功路径互斥。

**枚举的落盘取值是持久化契约**：`TapMode` 落盘为整数，`None = 0` / `Tap = 1` / `Hold = 2`；
`ScrollDirection` 落盘为整数，`Up = 0` / `Down = 1`。
 这些数值一旦发布即不得重排——配置文件里存的是数字，改动会让用户既有的任务静默变成另一种执行形态。
新增枚举成员只能**追加**在末尾；**新增落盘枚举一律入本清单**（本节是落盘枚举取值口径的唯一出处）。

### 7.2 损坏与兼容（FR-CFG-02/03）

| 场景 | 处理 |
|---|---|
| JSON 解析失败 / 结构不符 | **不崩溃**（FR-CFG-02）：捕获异常 → 提示用户 → 加载空配置（可用的最小状态）→ 保留损坏文件为 `.bak` 供排查 |
| 旧版本配置（缺字段/字段增减） | 读取时用**默认值补齐缺失字段**；版本号字段用于识别是否需要迁移；无法兼容时给出**明确提示**（FR-CFG-03） |
| 不提供导入导出 | 界面中**不存在**相关入口（FR-CFG-04） |

### 7.3 日志（FR-CFG-05）

#### 7.3.1 记录内容与调用契约

- **记录内容**（需求口径「任务启停、错误事件」的落地面）：
  - **任务启停**——**唯一汇点**是 `Scheduler.RunStateChanged`。`OnRunStateChanged` 内**先落盘再转发**，
    因此 Toggle / Stop / StopAll / Shutdown 四条路径的一致行为由这一处保证，不靠各调用点自觉。
  - **错误事件**——配置读写失败（`TaskRegistry` 保存失败分支）、输入注入失败（`InputSimulator`，
    文本**已过时间窗聚合且不含时间戳**，由落地点补时间戳）、钩子异常/失效。
- **调用契约**：日志接口 `ILogSink` 位于 `Core/Diagnostics`，只有**两个级别**——
  `Info` = 业务轨迹、`Error` = 异常轨迹（`Error` 另有 `Exception` 重载）；
  ①**任何调用不得让异常逸出**；②**不得在钩子回调路径上调用**（违反 §3.2）。
- **可空注入是硬要求**：各层对 `ILogSink` 的依赖一律为 `ILogSink?`（可选）——现有测试只传一个参数不受影响，
  未接日志的路径静默降级为不记，而非构造失败。
- **`LoadNotice` 不在日志面内**：配置载入通知走既有的 `LoadNotice` 通道（§7.2 的容错回退由它提示用户）；
  Logger 只承接**保存失败**分支，不承接载入失败——载入失败不写日志是本设计的明确口径，不是遗漏。

#### 7.3.2 落点与文件命名

- **目录**：配置目录下的 `logs\`（即 `%APPDATA%\鼠标键盘辅助\logs\`），复用 `JsonConfigStore.DefaultConfigDirectory()` 拼出，**不另拼一份路径逻辑**；
- **文件名**：`app-yyyyMMdd.log`（按自然日切分，一天一个文件）；
- **行格式**：`yyyy-MM-dd HH:mm:ss.fff [信息|错误] 正文`；异常**另起一行**、缩进 4 空格；
- **编码**：UTF-8 **无 BOM**。

#### 7.3.3 滚动与健壮性

- **滚动上限**：保留最近 `keepDays` 天（`DefaultKeepDays`，收敛下限为 1），避免无限增长（支撑 NFR-04 内存/磁盘稳定性）。
- **清理按文件名日期判定**：文件名里的日期**解析不出**一律**不删**（保护用户放进该目录的其他文件）；按自然日**跨天再清**。
- **写入策略**：**单入口一把锁**（不需要调用方保证线程安全）；**同步直接写盘，不设后台队列**——
  若走队列，退出前那一次日志会随进程消亡而丢失，而 AC-37 恰恰要求它在文件里。
- **失败短路**：IO 失败置内部 `_ioFailed` 后**短路后续写入**（不再反复重试拖慢业务）；全程吞异常。
- **空消息忽略**：空串/纯空白消息忽略，**且不因此创建文件**。
- **组合根**：全局唯一 Logger 在 `HostFacade` **最先**创建（早于 ConfigStore 与任务载入），再向下注入各层。

## 8. 关键机制汇总（设计决策 → 需求映射）

| 机制 | 设计决策 | 需求 |
|---|---|---|
| 输入模拟 | `SendInput` 单一出口；全局按住表（按符**引用计数** + 属主） | FR-CMD-*、FR-SEQ-07 |
| 注入失败 | 校验返回事件数 → 记日志（时间窗聚合）→ **不中断任务** | FR-CFG-05、NFR-04、NFR-06 |
| 补发松开 | 唯一入口 `ReleaseAll(属主)`；停止/紧急停止/退出三触发源共用 | FR-SEQ-07、FR-RUN-05、NFR-08 |
| 全局监听 | `WH_KEYBOARD_LL`/`WH_MOUSE_LL`；**钩子回调立即返回**；专用消息循环线程；静态回调防 GC 移动 | FR-TOGGLE-06、NFR-05 |
| 自注入过滤 | 钩子忽略 `LLKHF_INJECTED`/`LLMHF_INJECTED` 事件 | §6.1、NFR-07 |
| 开关消费 | 钩子返回值控制：`CallNextHookEx`（照常）vs 非零（吞掉）；逐任务可配、默认照常 | §6.1 |
| 并行执行 | 每条命令一个独立节拍器 | FR-SEQ-01/02 |
| 频率精度 | 绝对时间轴 + `timeBeginPeriod` + 专用线程；避免累积漂移 | NFR-02 |
| 并行隔离 | 高频命令专用线程、低频命令池化（阈值待实测校准） | NFR-03 |
| 停止 | 置标志 → 唤醒退出 → 补发松开；组合键**主键先松** | FR-SEQ-06/07、FR-TAP-06 |
| 紧急停止 | 钩子监听快捷键（**与开关共用回调，归属判定在 `isKeyDown` 早退之前**）→ `ToggleRequested` 载荷 `Guid?`（`null` = 紧急停止）→ 停止全部任务；**不吞键**；与任务开关键同键时各认 down/up、互不干扰 | FR-RUN-01~03、FR-RUN-07 |
| 配置 | JSON，`%APPDATA%`，原子写入，容错回退 | FR-CFG-01~03 |
| 日志 | 全局唯一 Logger（`HostFacade` 最先建）；`ILogSink?` 可空下注；落点 `%APPDATA%\...\logs\app-yyyyMMdd.log`；按文件名日期滚动 `keepDays` 天；单锁直写无队列；启停汇点 `RunStateChanged`（§7.3） | FR-CFG-05、NFR-04 |
| 单实例 | 命名互斥体 + `FindWindow`/`PostMessage(WM_APP)` 焦点移交（§6.4） | NFR-09、AC-30 |
| 托盘 | `Shell_NotifyIcon` + Win32 菜单（WinUI 无内建）；消息窗口取主窗口 HWND + 子类化（§6.3、§9.3 V-3） | FR-UI-01/02、AC-18 |
| 组合根 | `HostFacade`（Engine 层）装配全部模块、驱动开关命中链路（§2.2、§3.4.1） | FR-RUN-01~05、FR-TOGGLE-06 |
| 原生 UI | WinUI 3 / Fluent，随系统主题 | NFR-10 |
| 动画 | WinUI 过渡动画，响应"减少动画" | NFR-11 |
| 权限 | 清单请求管理员（`requireAdministrator`） | NFR-06、FR-RUN-01 |

> **权限口径（已裁定）**：清单无条件请求管理员，**正常运行路径即提权态**。因此“非管理员启动”不是常态运行场景，而是① 用户明确拒绝 UAC 提权、② 企业策略禁止提权 这两种情况；此时宿主进程根本不会启动，也就无“静默失效”可言。§10 的“非管理员启动时告知”指的是**启动失败路径**——该告知由 **Launcher 启动壳**（§2.2，独立可执行体，清单**不**请求提权）承担：它尝试启动宿主进程，捕获“提权被拒”失败，随即以普通权限弹出明确说明，给出“本工具需管理员权限，否则无法向管理员权限的窗口注入输入”及解决办法（NFR-06、AC-26），而不是让用户面对一个看似正常却处处无效的界面。
>
> **提权失败的判定信号（已实测，见 §9.3 V-7）**：Launcher 用 `Process.Start`（**必须** `UseShellExecute = true`）启动宿主；用户点 UAC「否」时抛 `Win32Exception`，`NativeErrorCode == 1223`（`ERROR_CANCELLED`）。判定以该错误码为准（与"文件缺失(2)""未用 ShellExecute(740)"可明确区分）；成功判定为"未抛异常"，**不得**用宿主退出码。该调用**同步阻塞至用户作答**。

**V-3 托盘消息窗口实测（已闭环）**

实测环境：Windows 11 22621，.NET SDK 8.0.101，x64；Windows App SDK **2.5.1**，`WindowsPackageType=None`。用独立探针工程 `tools/TrayProbe`（WinUI 3 单文件承载 `Program` / `App` / `MainWindow` / `TrayHost`，**不入 .sln**，用完即删）对照两种立图标手段，每种手段用**不同图标**区分，人工旁观验收。

| 手段 | 做法 | 结果 |
|---|---|---|
| **A（胜出）** | 取 **WinUI 3 主窗口的 HWND**（`WindowNative.GetWindowHandle(window)`，窗口 `Activated` 后取得）作为 `Shell_NotifyIcon` 的消息窗口，`SetWindowLongPtr(GWLP_WNDPROC)` 子类化以拦截自定义回调消息 | **四项全通过** |
| B（备选，未采用） | 另建一个专用 Win32 消息窗口（注册窗口类 + 自建消息循环）承接托盘回调 | 未走完（A 已全通过，无需再验） |

**验收结论（AC-1~AC-4 全通过）**：
1. 图标可见、可识别（未出现"图标不显示 / 显示为空白"）；
2. 左右键回调均能收到（`WM_LBUTTONUP` / `WM_RBUTTONUP` 自定义消息到达子类化窗口过程）；
3. 右键菜单可弹、可点、点击后**可正常消失**（弹出前 `SetForegroundWindow` 是菜单消失的必要前置，缺失时表现为"菜单点选项后不消失"）；
4. 连续运行 5 分钟图标不丢失（`Shell_NotifyIcon` 未被 explorer 清理）。

运行期实测：进程启动不崩溃（PID 存活，常驻内存约 20MB）；**无需 XAML 亦无需专用消息窗口**。

**对设计的影响（§6.3 定性）**：托盘的消息窗口**直接复用 WinUI 3 主窗口的 HWND**，不另建 Win32 消息窗口——这条原本列为"待验证"的选型由此定案。子类化窗口过程时须保存原 `WndProc` 并在默认分支转调，否则破坏 WinUI 窗口自身的消息处理。

**V-2 定时精度实测（已闭环）**

实测环境：Win10 22621，16 逻辑核，.NET 8.0.1，`Stopwatch` 10 MHz；用独立控制台探针（非 WinUI，定时基线不受 UI 框架干扰），测量各档频率下的偏差分布（均偏差 / P50 / P95 / P99 / 最大偏差）与达成率。

| 对照项 | 结果 | 对设计的影响 |
|---|---|---|
| `timeBeginPeriod(1)` 开 vs 关（专用线程） | 开：均偏差 0.001~0.017ms，P99 ≤0.47ms；**关：均偏差 5.6~6.2ms，P95/P99 达 12.5~14ms**（`Thread.Sleep(1)` 被系统 15.6ms 时钟粒度拉长） | **§4.2 第 1 条（必须调 `timeBeginPeriod(1)`）获得实测支撑**：差异达三个数量级 |
| 专用线程 vs 线程池（**均在 `timeBeginPeriod(1)` 生效下**） | 10~200 次/秒区间二者**精度无可区分**（均偏差均为微秒级）；线程池仅在 1 次/秒档出现单次 3.18ms 调度尖峰 | **精度不构成选择专用线程的理由**。保留专用线程是基于**可控性**（线程池线程数受全局并发影响、无法设 `Highest` 优先级、长驻任务占用池线程），此项**实测未推翻也未新增支持** |
| 真实等待策略（>2ms `Sleep(1)` 让出 CPU + 2ms 窗口内自旋）vs 纯自旋 | 200~500 次/秒二者差距在微秒级；纯自旋仅将最坏尖峰压低一档 | **不采用全程自旋**（换取微秒级收益而常驻占满一核不划算）——§4.2 策略成立 |
| 真实 `SendInput` 调用开销 | 各档均偏差 0.054~0.20ms（较纯定时升高约两个数量级，但仍为**亚毫秒**）；P95 ≤1.19ms；频率越高均偏差越小 | `SendInput` 单次调用**不主导抖动**；§4.2 无需为输入调用预留额外时间预算 |
| 多命令并行（5/10/20 条，最高合计 ~3600 次/秒调度压力） | 达成率 ≥99.3%，最大偏差 ≤15ms；500 次/秒档最大偏差 0.78~1.35ms | **并行本身非抖动主因**；§4.3 的并发规模控制成立 |
| 后台干扰（同优先级自旋突发，模拟密集抢占） | 10/50 次/秒无影响；**100~200 次/秒最大偏差恶化至 3.4~7.0ms**（P95/P99 仍 ≤0.74ms，达成率 100%） | 印证「钩子回调须短、须做心跳自检」的必要性（§3.2 / §8）。**注：该数字为同优先级 CPU 抢占的模拟上界，非真实钩子回调的预测值** |

**对 AC-23b 的支撑**：全部组别、全部档位的达成率均 ≥99.3%，远高于「平均频率 ≥90%」的判据 → AC-23b 判据余量充足。

**本次实测未覆盖（不影响上述结论，但限制其外推）**：
- 探针为**控制台**程序；WinUI 3 宿主下的实际精度**未测**（留实现期复测）；
- 干扰模拟为**独立线程自旋突发**，与真实 `WH_KEYBOARD_LL` 回调（运行在安装线程的消息循环上、由系统调用）特征不同，不能替代真实钩子场景的预测；
- 未模拟目标窗口对 `SendInput` 的处理耗时；
- 未覆盖多显示器 / 游戏内 DirectInput、其他进程高负载、节能电源计划等场景。
- 低频池化阈值的具体划分（§4.3 的 ≥50 次/秒分界）**未被本次数据单独校准**——实测表明 10~200 次/秒区间专用线程与线程池精度无可区分，故**阈值划分对精度不敏感**；§4.3 的分界保留为工程取舍（隔离性 / 线程数可控），不因精度理由而改动。

**V-7 Launcher 捕获宿主提权失败实测（已闭环）**

实测环境：Windows 11 22621（`EnableLUA=1`），.NET 8.0.101，x64；用两个临时探针工程——宿主（`requireAdministrator` 清单的最小控制台程序，启动成功即写标记文件）与启动壳（普通权限，`Process.Start` 启动宿主并如实记录异常类型 / `NativeErrorCode` / 返回对象 / 退出码 / 耗时），用完即删。

**补充实测（端到端，真实发布产物）**：以正式 `dotnet publish` 产出的 `Launcher.exe` + `鼠标键盘辅助.exe` 双文件在干净目录下实测：Launcher 退出码 **0**、无弹窗，随后**恰有一个宿主进程存活**（起始时间与启动时刻吻合）；该宿主在**普通权限 shell 中无法终止**（`Stop-Process` 报 `Access is denied`），据此确认清单 `requireAdministrator` 在真实分发形态下确实生效。

> **实现陷阱（已实测踩中并修复）**：单文件发布下 `AppContext.BaseDirectory` **不指向 exe 所在目录**，而是指向解压缓存 `%TEMP%\.net\<exe名>\<哈希>\`——据此定位宿主将**永远找不到**，Launcher 报"找不到主程序"退出 1。`Assembly.Location` 在单文件下同样不可用（返回空串）。**唯一正确依据是 `Environment.ProcessPath`**（返回真实 exe 全路径）。实测对照：`BaseDirectory` → `Exists=False`；`Environment.ProcessPath` → `Exists=True`。

**测得的失败码与行为**（`ProcessStartInfo.UseShellExecute` 的取值是在**同一宿主目标**下唯一改变的变量）：

| 场景 | `UseShellExecute` | `NativeErrorCode` | 行为 / 时机 | 对设计的影响 |
|---|---|---|---|---|
| 用户在 UAC 对话框点「否」 | `true` | **1223** `ERROR_CANCELLED` | 抛 `Win32Exception`；**`Start()` 同步阻塞至用户作答**（实测约 9.2s，为人工响应时间）；宿主**未启动**（标记文件未生成） | **§8 权限口径获得实测支撑**：Launcher 以捕获该异常作为"提权被拒"的**可靠判定信号**，随后弹出说明（NFR-06、AC-26） |
| 用户批准提权 | `true` | 无异常 | 返回 `Process` 对象；`ExitCode` 为**宿主自身**的退出码，与提权结果无关 | 成功判定不得依赖 `ExitCode`：宿主为常驻 GUI，须以"`Start()` 未抛异常"为成功；「是否已退出」不能用作判据 |
| 目标文件不存在 | `true` | **2** `ERROR_FILE_NOT_FOUND` | 抛 `Win32Exception`，不弹 UAC，立即返回（实测 14ms） | 与 1223 清晰区分；Launcher 可据 `NativeErrorCode` 分流提示文案 |
| **`UseShellExecute = false`（实现失误）** | `false` | **740** `ERROR_ELEVATION_REQUIRED` | 抛 `Win32Exception`，**不弹 UAC、直接失败**（实测 15ms） | ⚠️ **实现约束**：Launcher 启动宿主**必须**设 `UseShellExecute = true`；否则在正常提权机器上会以 740 直接失败，用户看到"启动失败"而非 UAC 提示，AC-26 直接失效 |

**结论**：
1. **判定信号可靠**——「提权被拒」由 `Win32Exception.NativeErrorCode == 1223` 唯一标识，与"文件缺失(2)""未用 ShellExecute(740)"等其他失败码可明确区分，不存在误判。
2. **`Start()` 是同步阻塞调用**——它阻塞至用户对 UAC 作答（批准或拒绝）才返回/抛出。因此 Launcher 的"启动中"状态须覆盖这段可能长达数十秒的等待（不可假设瞬时返回），真实的 UI 反馈应在**启动前**就绪。
3. **成功与失败的分界是"是否抛异常"**，不是退出码——宿主为常驻进程，`ExitCode` 语义不适用。

**本次实测未覆盖（限制结论外推）**：
- 仅测**管理员账户 + `ConsentPromptBehaviorAdmin` 提示态**；**标准用户**（须输入管理员凭据，`ConsentPromptBehaviorUser`）的取消路径**未测**——其 UAC 对话框形态不同，取消码预期同为 1223（`ShellExecuteEx` 层统一返回 `ERROR_CANCELLED`），但**未获本次数据验证**；
- 未测企业策略（`DisableElevation` / 软件限制策略）禁止提权时的返回码——设计上归入"启动失败"分支并提示用户，具体码留实现期实测；
- 未测 UAC 静默提升配置（`ConsentPromptBehaviorAdmin=0`）下的行为——该配置下**不出现对话框**，用户无从"拒绝"，`Start()` 直接成功（本实验中作为对照观察到：返回 `Process`、耗时 306ms）。

> **对实现期的直接约束（源自本次实测）**：Launcher 启动宿主必须 `UseShellExecute = true`；判定逻辑以 `NativeErrorCode` 为准（1223 = 用户取消提权）；成功判定为“未抛异常”，**不得**用 `ExitCode` 或“进程是否退出”判定；启动等待须按“可能阻塞至用户作答”设计。

**非打包单文件宿主的构建配方实测（已闭环）**

实测环境：Windows 11 22621，.NET SDK 8.0.101（仅此一个），Windows SDK 引用仅 10.0.22621.0（**无 26100**），x64；包源 `nuget.org`。由 WinUI 3 官方模板（MSIX 打包模式）改为非打包单文件，三次构建失败逐步定位。

| 约束 | 错误 / 表现 | 正确设定 |
|---|---|---|
| TFM 不得高于本机 SDK | `NETSDK1140`：`10.0.26100.0` 不是有效 `TargetPlatformVersion` | `net8.0-windows10.0.22621.0`（配 `<WindowsSdkPackageVersion>10.0.22621.38</WindowsSdkPackageVersion>`） |
| 单文件发布强制要求 MSIX 工具链 | `PublishSingleFile requires EnableMsixTooling for embedded resources.pri generation` | `<EnableMsixTooling>true</EnableMsixTooling>` |
| 入口前需设 Windows App SDK 运行时根目录 | `PublishSingleFile requires MICROSOFT_WINDOWSAPPRUNTIME_BASE_DIRECTORY to be set before program entry` | `<WindowsAppSdkUndockedRegFreeWinRTInitialize>true</WindowsAppSdkUndockedRegFreeWinRTInitialize>` |

**需澄清的两组概念**（易误判，均已实测验证）：

1. **`WindowsPackageType=None` 与 `EnableMsixTooling=true` 不矛盾**——前者决定“非打包”（不注册包标识、不需 MSIX 安装），后者保留的仅是用于生成 `resources.pri` 的 MSIX 工具链。单文件发布**必须**同时成立。
2. **`Microsoft.Windows.SDK.BuildTools` 是 NuGet 包，不要求本机安装同版本 Windows SDK**——其依赖链要求 `10.0.26100.4654`，与本机只有 22621 **不冲突**；反而**不应手写该引用**：手写旧版（如 `10.0.22621.756`）会与 WindowsAppSDK 的要求形成降级而触发 `NU1605`。让它由 WindowsAppSDK 依赖链带入即可。

**包版本选择**：`Microsoft.WindowsAppSDK` 稳定版序列为 `2.0.1` / `2.1.3` / `2.2.0` / `2.3.1` / `2.4.0` / `2.5.1`（**无 2.0.4**，该错号来自 `WindowsAppSDK.Base` 子包版本，勿混淆）。`2.0.1` 及以后的稳定版**均**经 `Base` 依赖 `SDK.BuildTools 10.0.26100.4654`，无法靠降版避开——本条不构成选版理由。当前取 **`2.5.1`** 并写死。

**验证结果**（`dotnet publish src\Host\Host.csproj -c Release`）：0 警告 0 错误；产物为**单个 exe**，约 217 MB（`Host.pdb` 为调试符号）。**运行时实测**：进程启动后存活不崩溃（自包含，本机未装 Windows App SDK 运行时）；且**普通权限无法终止**（`Access is denied`）——同时印证清单 `requireAdministrator` 确实生效。

**本次实测未覆盖**：仅测 x64；未测 ARM64 / x86 的发布产物；未测开启 `PublishTrimmed` 的效果（当前保守关闭，XAML/WinRT 依赖反射）；宿主的实际 UI 功能未验证（骨架阶段，仅空窗口）。

## 10. 安全与边界

- **权限**：该工具本质上需要管理员权限才能向高完整性窗口注入输入（UIPI 限制，见 §3.1）。清单无条件请求提权（§8），因此正常路径即提权运行；**提权被拒（用户取消 UAC / 策略禁止）导致启动失败时，明确告知用户原因与解决办法**（NFR-06、AC-26），而非静默失效；
- **不干扰**：未运行时/禁用任务不得产生任何输入（NFR-07、AC-25）；实现上确保节拍器只由"启动"流程创建，停止流程彻底销毁；
- **可关闭性**：托盘退出与紧急停止是两条独立路径，均必须能立即终止全部模拟输入（NFR-08、AC-32）；
- **使用边界**：不做反检测设计（N7、§6.3 需求原文的边界声明）。

## 13. 验证方式（与 AC 集合的关系）
本设计**不**重复定义验收标准——AC-01~AC-37 的权威定义在需求文档 §7。本节只说明设计侧如何使各 AC 具备**可验证性**：

| 验证层次 | 手段 | 覆盖的 AC 类别 |
|---|---|---|
| 逻辑正确性 | 校验器单测（§5.3 全校验清单逐条对照） | 输入校验类 AC（非法频率、重名、开关键冲突等） |
| 输入注入正确性 | **分两层**（见下方说明）：注入**决策**逻辑用假出口单测；事件是否真的到达目标程序用目标程序侧监测（记事本/自建窗口接收按键） | 命令执行类 AC（点按/按住/组合键/鼠标/滚轮） |
| 时序精度 | 高精度计时器记录实际间隔，对照频率目标 | NFR-02 相关 AC（1~50 次/秒区间对照 ±20ms；50 次/秒以上对照平均频率≥90%，见 §4.2） |
| 钩子行为 | 实测 injected 标志、开关消费、超时移除（§9.2 V-1/V-4） | 开关类、稳定性类 AC |
| 持久化与容错 | 人为构造损坏 JSON / 旧版配置，观察行为 | FR-CFG-02/03 相关 AC |

> **测试层的归属**：需求文档与本文档均为设计阶段产物；**独立的验收测试文档尚未建立**。测试层建立时，应按本表结构逐条把 AC-xx 映射到具体测试用例（**拆出独立文档须在 `docs/README.md` 登记**），本文档不代行其职。

### 13.1 输入注入的两层可测性（§3.1 的测试口径）

“输入注入正确性”在上表中拆为两层，因为这两类事实的**验证手段根本不同**：

| 层 | 验证对象 | 手段 | 是否进单测 |
|---|---|---|---|
| 注入**决策**层 | 引用计数、属主归属、补发顺序、失败不中断与日志聚合（§3.1.1~3.1.3） | `InputSimulator` + 假 `IInputSink` + 假时钟 | **进**（`Host.Tests`） |
| 注入**下落**层 | 事件是否真的到达目标程序、坐标是否准确、滚轮格数是否对 | 目标程序侧监测（记事本 / 坐标回读工具 / 固定测试程序） | **不进**（见下） |

**为何下落层不进单测**：该层没有可断言的逻辑，只有平台调用——它的正确性事实是“目标程序收到了什么”，而目标程序不在测试进程内。单测里能断言的只是“我们向 `SendInput` 传了什么”，那不是同一件事，把它写成绿色测试反而会造出“已覆盖”的假象。该层一律由 AC 的实机验证（AC-11/12/12a/14b 等）承担。

**因此定了这条接口边界**：`IInputSink`（纯逻辑层的注入出口）在 Core，可被单测替换；`SendInput` 的真实调用集中在 Host 的单一薄类里，**Host 不列入测试工程的引用**（`docs/README.md:47` 已明示 SendInput 类验收不进单测）。
